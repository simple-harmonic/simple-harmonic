# 05 — Tool System: Server Tools, Sandbox, and Custom API Tools

This document covers the server-side tool implementations in `packages/backend/src/server/tools/` and the custom-tool data files in `.simple-harmonic/skills/`. Tools are the only way agents act on the world. Each tool is a (definition, implementation) pair registered into a `ToolRegistry` (`packages/backend/src/lib/meta-agent/registry.ts`): the definition carries the name, description, category, risk label, and a Zod schema; the implementation is an async function that receives schema-validated arguments plus a run context (`teamId`, `agentId`, `agentName`, peers, a2ax sender — `packages/backend/src/lib/meta-agent/tools.ts:31-41`) and returns a structured result that never throws. The app assembles 15 built-in tools (3 internal message-passing tools from the library layer plus 12 server tools doing real I/O), then layers on custom API tools defined as flat JSON files at `.simple-harmonic/skills/<name>.json`. Safety comes from four orthogonal mechanisms: a filesystem jail, an SSRF egress guard with DNS pinning, an environment-scrubbing policy for subprocesses, and a two-level destructive gate (the `SH_ENABLE_TOOLS` kill switch plus the per-call human approval flow driven by the registry's risk labels).

## Registry assembly and wiring

`createAppRegistry()` (`packages/backend/src/server/tools/index.ts:45`) starts from `createDefaultRegistry()` (`packages/backend/src/lib/meta-agent/default-tools.ts:46`), which registers the three internal tools (`send_message`, `broadcast`, `report_action`), then registers the 12 app tools: `read_file`, `write_file`, `run_command`, `coding_task`, `http_fetch`, `github_api`, `set_team_goal`, `spawn_sub_team`, `modify_agent`, `modify_team`, `action_history`, `observe_app`. `createAppRegistryWithCustomTools()` (`index.ts:68`) additionally calls `listCustomToolFiles()` (`packages/backend/src/server/custom-tools.ts:39`) and registers every discovered file via `buildApiToolDef`/`buildApiToolImpl` (`packages/backend/src/server/tools/api-tool-runtime.ts:20,58`), skipping any custom tool whose name collides with an already-registered tool; loader failures are swallowed (custom tools silently absent). The swallowing `try/catch` wraps the whole loop, not each iteration (`index.ts:71-81`), so a file that passes the loader's checks but whose def construction throws (e.g. a `config` missing `allowedMethods`, which crashes `buildApiToolDef` at `api-tool-runtime.ts:25`) silently drops every custom tool not yet registered, not just itself. The registry itself throws on duplicate registration (`registry.ts:83`).

Consumers (route handler bodies live in `packages/backend/src/server/api/**`; the Next.js files under `src/app/api/` are thin re-exports, and the standalone host serves the same handlers):

- The tick loop builds a fresh `createAppRegistryWithCustomTools()` per team per tick (`packages/backend/src/server/api/tick.ts:195`) and passes it to the runner/harness with `tools: agent.tools` from the agent's store row (`tick.ts:388` on the run path, `tick.ts:507` on the resume path).
- The skills settings API uses `createAppRegistry()` (built-ins only) to list tool metadata and to validate the names in an agent's tool allowlist on PATCH (`packages/backend/src/server/api/settings/skills.ts:16,61-66`).
- `index.ts:112-117` re-exports the sandbox primitives (`toolsRoot`, `toolsEnabled`, `resolveInJail`, `JailEscapeError`) for other modules.

## Tool catalog

"Approval" means the registry labels the call destructive, so the run suspends before execution. In the legacy runner the whole round suspends and the pending calls return to the caller (`packages/backend/src/lib/meta-agent/runner.ts:356-391`); in codex engine mode (selected when the API key source is codex and `SH_CODEX_RUNTIME !== "exec"`, `tick.ts:164`) the app-server harness applies the same `registry.isDestructive` gate to each dynamic-tool call and interrupts the turn (`packages/backend/src/lib/meta-agent/codex-harness.ts:139,253-267`). Either way the tick handler parks the agent and persists the pending calls as approval records for a human decision via the `approvals` repo, `approvals.insertMany(...)` (`tick.ts:661`), which writes them to the agent's `approvals.json` file — the store-agnostic runner/harness never writes them itself. "Kill switch" means the implementation additionally refuses to run unless `SH_ENABLE_TOOLS` is set — these are independent gates.

| Tool | Module | Risk / approval | Kill switch | Behavior |
|---|---|---|---|---|
| `send_message` | internal (lib) | safe | no | Direct a2ax message to a named peer |
| `broadcast` | internal (lib) | safe | no | a2ax message to all team peers |
| `report_action` | internal (lib) | safe | no | Logs an action entry (`{summary, ...details}`) |
| `read_file` | filesystem | safe | no | Reads a UTF-8 file inside the jail; sensitive paths denied |
| `write_file` | filesystem | destructive | yes | Writes a UTF-8 file inside the jail, mkdir -p parents |
| `run_command` | shell | destructive | yes | `execFile` of an allowlisted program, no shell, scrubbed env |
| `coding_task` | shell (coding/) | destructive | yes | Runs an autonomous coding-CLI subprocess (codex / claude-code / opencode) |
| `http_fetch` | network | safe | no | HTTPS GET of a public URL through the SSRF guard |
| `github_api` | network | destructive on non-GET (arg-aware) | yes, writes only | GitHub REST call; writes also need `GITHUB_TOKEN` |
| `set_team_goal` | management | destructive | no | Updates a team's `goal` field in `team.json` (sub-tree scoped) |
| `spawn_sub_team` | management | destructive | no | Creates a child team folder + agent folders |
| `modify_agent` | management | destructive | no | Update / delete / move an agent (sub-tree scoped) |
| `modify_team` | management | destructive | no | Update or recursively delete a team folder (sub-tree scoped) |
| `action_history` | action-history | safe | no | Reads `actions.jsonl` for self / agent / team sub-tree |

`packages/backend/tests/unit/server-tools.test.ts:365-407` pins the exact 15-tool set (`toHaveLength(15)` at line 400) and pins the destructive set to `coding_task`, `github_api`, `modify_agent`, `modify_team`, `run_command`, `set_team_goal`, `spawn_sub_team`, `write_file`. Note the asymmetry: the management tools and custom API-tool writes pass only through the approval gate, not the `SH_ENABLE_TOOLS` switch; the switch covers `write_file`, `run_command`, `coding_task`, and mutating `github_api` calls.

## Module detail

### Filesystem (`packages/backend/src/server/tools/filesystem.ts`)

**`read_file`** — schema `{ path: string }` (relative to the project root). Implementation (`filesystem.ts:49`): resolves the path through the symlink-aware jail (`resolveInJailReal`), then rejects sensitive paths via `isSensitivePath` (`filesystem.ts:150`), rejects non-files, rejects files over 256 KiB (`MAX_READ_BYTES`, `filesystem.ts:18`), and returns the full UTF-8 contents. Emits a `file_read` action with a 2,000-char output snippet. Errors are mapped to friendly strings (`errToMessage`, `filesystem.ts:141`): `JailEscapeError` message, `ENOENT` → "File not found", `EACCES` → "Permission denied", `EISDIR` → "Path is a directory". The schema description steers agents toward `.simple-harmonic/skills/` and `.simple-harmonic/connectors/` — file discovery via `read_file` **is** the custom-tool discovery mechanism.

The sensitive-path denylist (applied to the jail-relative path, case-insensitive): `.simple-harmonic/secrets.json`; anything under `.apollo/`; any basename starting with `.env` unless it ends `.example`/`.sample`/`.template`; `.npmrc`, `.pypirc`, `.netrc`; `id_rsa`/`id_dsa`/`id_ecdsa`/`id_ed25519`; any `*.pem` or `*.key`; and any `.ssh` directory component (`filesystem.ts:150-161`). This denylist applies **only to `read_file`** — `write_file` performs no sensitive-path check (`filesystem.ts:107-139`), so with the kill switch on it can overwrite any jailed path including `.env` files.

**`write_file`** — schema `{ path: string, content: string }`. Refuses with a fixed message when `toolsEnabled()` is false (`filesystem.ts:108`). Otherwise resolves through `resolveInJailReal`, creates parent directories recursively, and overwrites the file. Emits `file_written` with the relative path and char count.

### Shell (`packages/backend/src/server/tools/shell.ts`)

**`run_command`** — schema `{ command: string, args?: string[] }`. Gated by `toolsEnabled()` (`shell.ts:109`). Execution model (`shell.ts:149-204`): `execFile` with a literal argv — there is **no shell**, so `|`, `;`, `&&`, `$()`, backticks are inert tokens (verified end-to-end in `packages/backend/tests/unit/security/tools-security.test.ts:156-179`). Constraints, checked in order:

1. The program must be in `ALLOWED_PROGRAMS` (`shell.ts:29`): `git`, `ls`, `cat`, `rg`, `grep`, `find`, `diff`, `tsc`, `vitest`, `npm`, `npx`, `biome`, `echo`, `pwd`, `wc`, `head`, `tail`, `mkdir`, `cp`, `mv`, `sort`, `uniq`, `tr` (23 programs; interpreters like `node`/`python` are deliberately absent).
2. Every argument is screened by `isEscapingArg` (`shell.ts:207`): rejects null bytes, absolute paths (`/...`), `~` and `~/...`, any `..` traversal form, and the git-redirection flags `--git-dir=`, `--work-tree=`, `--output=`, `--exec-path=`.
3. For `git`, the first argument must be in `ALLOWED_GIT_SUBCOMMANDS` (`shell.ts:59`): read-only `status`, `log`, `diff`, `show`, `rev-parse`, `ls-files`, `grep`, `blame`, `branch`, `stash`, plus write subcommands `add`, `commit`, `push`, `pull`, `fetch`, `checkout`, `switch`, `merge`, `rebase`, `cherry-pick`, `restore`, `reset`, `tag` (write subcommands are permitted because `run_command` is itself approval-gated).

Runtime limits: `cwd` pinned to `toolsRoot()`, 30 s timeout (`TIMEOUT_MS`), 64 KiB output cap (`MAX_OUTPUT_BYTES`), and the child env is `scrubbedEnv()` — secrets are stripped (verified in `tools-security.test.ts:219-256`). stderr is appended to stdout under a `[stderr]` marker; a killed (timed-out) process returns a timeout failure; non-zero exit returns the combined output as a failure. Success emits a `command_run` action with a 2,000-char snippet.

### Network (`packages/backend/src/server/tools/network.ts`)

**`http_fetch`** — schema `{ url: string }` (must parse as a URL). Safe and ungated: GET is the only method. Implementation (`network.ts:39`): `assertPublicAndResolve` validates the URL and returns a pinned public IP, then `proxyFetch` performs the request with that pin; 20 s abort timeout (`FETCH_TIMEOUT_MS`), response body read with a streaming 128 KiB cap (`readCappedText`, `network.ts:183`, which counts total bytes read but keeps only the cap). `success` mirrors `res.ok`; non-2xx returns `HTTP <status> <statusText>: <first 2000 chars>`. Emits `http_fetched` with url, status, bytes, and a 2,000-char snippet.

**`github_api`** — schema `{ method: "GET"|"POST"|"PATCH"|"PUT"|"DELETE", path: string, body?: Record<string,unknown> }`. Risk is argument-aware: `isDestructive: (args) => args.method !== "GET"` (`network.ts:99`). Non-GET requires both `toolsEnabled()` (`network.ts:106`) and a resolvable `GITHUB_TOKEN` (via `resolveConnector`, i.e. `.simple-harmonic/secrets.json` first, then `process.env`); GET runs without either, attaching the token only if present. `path` must start with `/` (`network.ts:124`). The URL is fixed to `https://api.github.com<path>` and still goes through `assertPublicAndResolve` for the pin. Headers: `Accept: application/vnd.github+json`, `User-Agent: simple-harmonic-agent`, `Authorization: Bearer <token>` when available, `Content-Type: application/json` when a body is sent. Same 20 s timeout and 128 KiB cap. Emits `github_api_called`.

Both tools route through `proxyFetch` (`packages/backend/src/server/proxy-fetch.ts:130`), which honors `HTTPS_PROXY`/`HTTP_PROXY` (and lowercase variants) via an HTTP CONNECT tunnel, falls back to the macOS system proxy (`scutil --proxy`, cached), and otherwise does a direct `https.request` with the DNS lookup overridden to the pinned IP while keeping the hostname for TLS SNI and certificate verification (`proxy-fetch.ts:53-55,89-90`). On the proxy path no pin is applied (the proxy resolves the host itself).

### Management (`packages/backend/src/server/tools/management.ts`)

All four tools are `internal`/`destructive` and operate through the store repos (`agents`, `teams` from `../store`), not SQL — `management.ts` no longer imports `db()`, Drizzle, or the deleted `chatSessions`/`chatMessages`/`pendingApprovals`/`actionLog` schema tables. They share two helpers: `resolveTeamId` (name → id by scanning `teams.all()`, defaulting to the caller's team) and `assertInSubTree` (`management.ts:23`), which loads the caller's team sub-tree via `getSubTreeIds` and rejects any target outside it — an agent can only manage its own team and descendants.

**`set_team_goal`** — schema `{ team_name?: string, goal: string }`. Calls `teams.update(teamId, { goal })`, which rewrites the `goal` field in the team's `team.json` (`management.ts:72`). Emits `team_goal_set`.

**`modify_team`** — schema `{ team_name: string, action: "update"|"delete", updates?: { name?, goal?, paused? } }`. `delete` refuses the caller's own team, then counts the doomed agents (`agents.byTeams(getSubTreeIds(teamId))`) for the report message and calls `teams.delete(teamId)` (`management.ts:129-131`). The delete is a single `rmdir` of the team's folder: because sub-teams nest recursively under `teams/<subTeamId>/` and each agent folder, its `approvals.json`/`actions.jsonl`/`trace.jsonl`, and the team's a2ax `messages/` all live inside the team directory, one `removePath` (`store/fs-store.ts:101`, `rmSync` recursive) erases the entire sub-tree at once — there is no dependency-ordered multi-table cascade, no transaction, and no foreign keys to satisfy. The action payload still reports `agentsDeleted` plus `teamsDeleted: subTreeIds.size`. `update` applies any of `name`/`goal`/`paused` via `teams.update` and fails if no fields were given. Emits `team_deleted` or `team_modified`.

**`spawn_sub_team`** — schema `{ team_name: string, agents: Array<{ name, role, archetype, tools: string[], schedule_seconds: number, initial_prompt }> }`. Calls `teams.insert({ name, parentTeamId: ctx.teamId })` — which creates the new team's folder under the caller's `teams/` children dir — then `agents.insertMany(team.id, …)` writing one `agent.json` folder per agent with staggered `nextRunAt` (now + schedule + 2 s per index) (`management.ts:209-224`). No separate chat-session row is created any more (chat is a2ax messages persisted under the team folder on first use). There is no per-agent `output_contract` parameter here. Emits `sub_team_spawned`.

**`modify_agent`** — schema `{ agent_name: string, team_name?: string, action?: "update"|"delete"|"move", move_to_team?: string, updates?: { tools?, initial_prompt?, schedule_seconds?, status?: "running"|"paused", role?, output_contract? } }` (default action `update`). The agent is located with `agents.byTeam(targetTeamId).find(name)`. Authorization checks the target team's membership in the caller's sub-tree; `move` re-checks the destination team too. Self-deletion is unconditionally blocked (`management.ts:295`). `delete` is `agents.delete(agent.id)` — a single `rmdir` of the agent's folder (its `agent.json` plus `approvals.json`/`actions.jsonl`/`trace.jsonl`), no separate approval/action cleanup. `move` is `agents.move(agent.id, destTeam.id)`, which rewrites `teamId` in `agent.json` and `renameSync`-relocates the agent folder under the destination team. `update` maps the snake_case fields onto the row fields and calls `agents.update`. Emits `agent_deleted` / `agent_moved` / `agent_modified`.

### Observability

**`observe_app`** (`packages/backend/src/server/tools/observe.ts`) — schema `{ severity?: "info"|"warning"|"error", level?: "agent"|"team"|"tool", source?: string, hours?: number, limit?: number }`. Defaults/caps: 1 hour back (max 24), 20 events (max 50). Calls `queryAppEvents` with the caller's `teamId` and a hard-coded `includeInfra: false` — infrastructure-level events are never returned to agents (`observe.ts:61`). Returns the formatted event list or a "No events found" success. Emits `app_observed`.

**`action_history`** (`packages/backend/src/server/tools/action-history.ts`) — schema `{ scope: "agent"|"team"|"self", agent_name?, team_name?, limit?, validation_only? }`. `self` targets the caller; `agent` requires `agent_name` (global lookup via `agents.all().find(name)`, **not** sub-tree restricted); `team` resolves a team (default own) and collects all agents in its sub-tree (`agents.byTeams(getSubTreeIds(teamId))`). Fetches up to `2 × limit` newest entries via `actionLog.byAgents(ids, { limit: limit*2 })` (limit default 20, max 50); that repo reads each target agent's `actions.jsonl`, merges across agents, and sorts newest-first — the file-store equivalent of the old `ORDER BY executed_at DESC` (`store/repos/action-log.ts:48-60`). It extracts any `payload.validation` (`{valid, issues[]}`), optionally filters to validated entries, and renders one line per entry: `[HH:MM:SS] agent · actionType: summary [PASS]` or `[FAIL: path: message; …]`. `summarize` (`action-history.ts:173`) prefers `payload.summary`/`conclusion`/`message`, then `tool(args)`, then truncated JSON.

### Coding subsystem (`packages/backend/src/server/tools/coding/`)

This subsystem is untouched by the entire PR train, including PR #16: `git log` shows `packages/backend/src/server/tools/coding/` unchanged since the initial commit — the file-store migration rewired only how the management and action-history tools persist (`management.ts`, `action-history.ts`) and moved the `ApiToolConfig` import in `api-tool-runtime.ts`/`custom-tools.ts` (both now import it from `../store/types`), leaving `coding/` and the coding-subprocess machinery alone. The only PR #16 touch to `sandbox.ts` was unrelated: a one-line edit to the `codingEnv` doc comment dropping `DATABASE_URL` from its secret-exclusion list (`sandbox.ts:123`). Note that `coding_task` (a one-shot CLI subprocess) is unrelated to the codex *engine mode* of PR #12, which replaces the agent tick loop itself.

**`coding_task`** (`coding/index.ts:95`) — schema `{ task: string, scope?: string, model?: string }`, category `shell`, risk `destructive`. Gated by `toolsEnabled()` (`coding/index.ts:109`). Engine selection (`createCodingBackend`, `coding/index.ts:27`): the backend name comes from `getConfig().codingBackend` (`packages/backend/src/server/config.ts:58-66`), resolved as `simple-harmonic.config.json` `codingBackend` field → `SH_CODING_BACKEND` env var → default `"codex"`, validated against the set `codex | claude-code | opencode` (invalid names fall back to `codex`; `packages/backend/tests/unit/coding-config.test.ts` pins this). No `simple-harmonic.config.json` exists on disk right now (it was swept into `stash@{0}`, see the parked note below), so resolution is effectively env var → default. Per-backend config (`codingConfig[backend]`) supplies an optional default `model` and a `timeout` in **seconds** (multiplied by 1000 at `coding/index.ts:129`); with no config file both are unset, so each backend uses its built-in 5-minute timeout and the CLI's own default model. If `scope` is given the task prompt is prefixed with `Focus on: <scope>\n\n`. The backend's `CodingResult` (`coding/types.ts:18`: `messages[]`, `commands[{command, output, exitCode}]`, `errors[]`) is rendered by `buildSummary` (`coding/index.ts:38`): errors block, commands block (first 5 output lines each), and the last message as "Agent conclusion" (4,000-char cap). The call is reported as failure only when there are errors **and** zero messages; otherwise success, emitting `coding_task_completed` with backend name, truncated task, scope, command count, and a 2,000-char conclusion.

**Shared subprocess lifecycle** (`coding/run-subprocess.ts:28`): before spawning, the cwd is re-validated through `resolveInJail` (a cwd outside the jail rejects the promise). The child is spawned with `stdio: ["ignore","pipe","pipe"]` and `env: codingEnv(envKeys)` — the scrubbed base allowlist plus only the named provider keys; key names must match `/^[A-Z][A-Z0-9_]*$/` or they are ignored (`sandbox.ts:128`, verified in `coding-env.test.ts` and `run-subprocess.test.ts`). Timeout (default 5 min per backend) sends SIGTERM and **resolves** with the partial parse plus a `Timed out after Ns` error. An `AbortSignal` rejects. stdout is capped at 256 KiB keeping the **tail**, truncated at a line boundary so a JSONL record is never cut mid-line (`run-subprocess.ts:81-92`); stderr chunks are each capped at 8,192 bytes. Spawn failure resolves with an error result; a non-zero exit with no parsed messages appends stderr (or an exit-code message) to `errors`.

The three engines differ only in argv, forwarded env keys, and JSONL parsing:

| Engine | Command line | Env keys forwarded | Output parsing |
|---|---|---|---|
| `claude-code` (`coding/claude-code.ts`) | `claude -p --output-format stream-json --verbose --dangerously-skip-permissions --no-session-persistence [--model M] <task>` | `ANTHROPIC_API_KEY` | `assistant` events: `text` blocks → messages, `tool_use` blocks → commands (command = `input.command` or tool name, output = `input.description`, exitCode 0); `result` events appended if novel; `error` events → errors |
| `codex` (`coding/codex.ts`) | `codex exec --json --skip-git-repo-check -s workspace-write -C <cwd> [-m M] <task>` | `CODEX_HOME`, `OPENAI_API_KEY` (Codex auth is otherwise file-based under `HOME`, which the scrubbed env keeps) | `item.completed` with `item.type === "agent_message"` → messages; `item.type === "tool_call"` with `status === "completed"` → commands (`aggregated_output` capped at 2,000, `exit_code ?? -1`); `error` events → errors |
| `opencode` (`coding/opencode.ts`) | `opencode run --format json -q --working-dir <cwd> [--model M] <task>` | `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` | `text` events → messages; `tool_use` → commands; `step_finish` with `reason === "stop"` → messages; `error` → errors |

There is **no session or resume support** in this subsystem: every `coding_task` invocation is a fresh one-shot subprocess, and the claude-code backend explicitly passes `--no-session-persistence`. The `claude-code` backend runs with `--dangerously-skip-permissions`, which the code accepts because the cwd is jailed, the env is scrubbed, and `coding_task` is itself double-gated (kill switch + approval).

## Security mechanisms

### Filesystem jail (`packages/backend/src/server/tools/sandbox.ts`)

- `toolsRoot()` (`sandbox.ts:24`) — the jail root: `SH_TOOLS_CWD` if set, otherwise `process.cwd()`. All filesystem paths, the shell cwd, and the coding-subprocess cwd resolve against it. The skills and connectors directories also live under it (`custom-tools.ts:35-37`, `connectors.ts:29`).
- `toolsEnabled()` (`sandbox.ts:36`) — the destructive kill switch: true only when `SH_ENABLE_TOOLS` is `1`, `true`, or `yes` (case-insensitive). Default OFF.
- `resolveInJail(p)` (`sandbox.ts:58`) — synchronous logical containment: rejects null bytes, then resolves the path against the root and rejects anything whose `relative()` result starts with `..` or is absolute. Throws `JailEscapeError`.
- `resolveInJailReal(p)` (`sandbox.ts:89`) — the symlink-aware check used by both filesystem tools: after the logical check, it realpaths the jail root (so a root under `/tmp` → `/private/tmp` on macOS compares correctly) and realpaths the deepest **existing** ancestor of the target (`realpathDeepestExisting`, `sandbox.ts:154`), re-appending the non-existent tail (which cannot itself be a symlink). If the effective real location escapes the real root, it throws. This means a symlink inside the jail pointing outside is rejected, not followed; a symlink that stays inside is allowed (`tools-security.test.ts:108-153`).
- `scrubbedEnv()` (`sandbox.ts:110`) — child-process env reduced to the allowlist `PATH, HOME, USER, SHELL, LANG, LC_ALL, TMPDIR, TZ`; every other variable (API keys, `GITHUB_TOKEN`, `APOLLO_MASTER_KEY`, tokens) is dropped. (The file store keeps no connection-string secret to strip — there is no `DATABASE_URL`; data lives on local disk under `SH_DATA_DIR`.)
- `codingEnv(extraKeys)` (`sandbox.ts:128`) — `scrubbedEnv()` plus only the explicitly named, uppercase-validated provider keys.

### SSRF egress guard (`packages/backend/src/server/tools/url-guard.ts`)

`assertPublicAndResolve(rawUrl)` (`url-guard.ts:67`) is the single egress policy for every agent-driven outbound request (`http_fetch`, `github_api`, and custom API tools) and runs **before** any connector secret is attached. It rejects:

- any non-`https:` scheme;
- URLs with embedded credentials (`user:pass@`);
- `localhost` and any `*.localhost` host (after lowercasing, stripping a trailing dot, and stripping IPv6 brackets);
- IP-literal hosts in private ranges, with no DNS lookup;
- DNS names where **any** resolved address is private (a mixed public+private record set is rejected wholesale, so rebinding via a poisoned record set cannot slip through);
- DNS failures and empty record sets.

Private IPv4 ranges (`isPrivateIpv4`, `url-guard.ts:22`): `0.*`, `10.*`, `127.*` (loopback), `100.64–127.*` (CGNAT), `169.254.*` (link-local / cloud metadata), `172.16–31.*`, `192.168.*`, `198.18–19.*` (benchmarking), and everything `>= 224.*` (multicast/reserved). Private IPv6 (`isPrivateIpv6`, `url-guard.ts:37`): `::1`, `::`, `fc`/`fd` ULA prefixes, `fe80` link-local, and `::ffff:`-mapped addresses checked as IPv4.

On success it returns a **pinned** public IP (preferring IPv4) which `proxyFetch` uses to override DNS at connect time while preserving the hostname for TLS SNI/cert verification — closing the DNS-rebinding TOCTOU between validation and connection. Coverage: `packages/backend/tests/unit/security/url-guard.test.ts` (ranges, literals, mixed record sets, pinning) and `packages/backend/tests/unit/api-tool-ssrf.test.ts` (a custom tool whose `baseUrl` resolves privately is blocked and the bearer token is never sent).

### Destructive gating and approval

Two independent layers:

1. **Kill switch** — `write_file`, `run_command`, `coding_task`, and mutating `github_api` calls hard-fail in their impls when `SH_ENABLE_TOOLS` is unset, regardless of approval state. The switch applies identically under both runtimes, because the impls themselves check it.
2. **Approval gate** — `ToolRegistry.isDestructive(name, args)` (`registry.ts:130`) returns true for unknown tool names (fail-safe), consults the def's argument-aware `isDestructive(args)` when present (treating unparseable args as destructive), and otherwise uses the static `risk` label. The runner classifies every tool call in a round before executing anything; if any call is destructive it suspends the whole round and returns the pending calls in its result (`runner.ts:356-391`). The codex app-server harness applies the same classifier per dynamic-tool call and interrupts the turn (`codex-harness.ts:253-267`). The tick handler then parks the agent and persists the pending calls via `approvals.insertMany(...)` to the agent's `approvals.json` (`packages/backend/src/server/api/tick.ts:661`).

The registry also Zod-validates all LLM-supplied arguments before any impl runs; malformed args, missing fields, and unknown tools come back as structured `success: false` results, never exceptions (`registry.ts:147-174`, `tools-security.test.ts:258-290`).

## Declarative API tools (`packages/backend/src/server/tools/api-tool-runtime.ts`)

A custom tool file's `config` (typed as `ApiToolConfig`, `packages/backend/src/server/store/types.ts:121` — moved here from the deleted `db/schema.ts` as a shared type, never backed by any table: `{ baseUrl, connectorKey, authHeader?, authPrefix?, allowedMethods, defaultHeaders?, pathPrefix? }`) becomes a callable HTTP tool:

- **Definition** (`buildApiToolDef`, `api-tool-runtime.ts:20`): schema `{ method: enum(allowedMethods, falling back to ["GET"] when the array is empty), path: string, body?: Record<string,unknown>, query?: Record<string,string> }`; category `network`; risk `destructive` with `isDestructive: method !== "GET"` (`api-tool-runtime.ts:53`) — so GET calls on an API tool run without approval, writes gate.
- **Implementation** (`buildApiToolImpl`, `api-tool-runtime.ts:58`), in order:
  1. Resolve the auth value via `resolveConnector(config.connectorKey)` (`packages/backend/src/server/connectors.ts:53`: `.simple-harmonic/secrets.json` first, then `process.env`). A missing connector fails the call **only for non-GET methods**; GET proceeds unauthenticated.
  2. Build the URL as `baseUrl + pathPrefix + path` (a leading slash is added to `path` if missing) and set query params.
  3. Run `assertPublicAndResolve` on the full URL **before attaching the secret** — a tool whose `baseUrl` points at an internal or metadata host fails here and the bearer token never leaves the box.
  4. Build headers: `User-Agent: simple-harmonic-agent`, then `config.defaultHeaders`, then the auth header (`config.authHeader` default `Authorization`, value `"<authPrefix> <token>"` with prefix default `Bearer`; an explicit empty-string prefix sends the raw value), plus `Content-Type: application/json` when a body is present.
  5. `proxyFetch` with the IP pin, 20 s timeout, JSON-serialized body, response read with a 128 KiB cap (`readCapped`, `api-tool-runtime.ts:168`).
  6. `success` mirrors `res.ok`; failures format as `HTTP <status> <statusText>: <body slice>`. Emits an `api_tool_called` action with method, path, status, and a 2,000-char output snippet.

Behavior contracts are pinned in `packages/backend/tests/unit/api-tool-runtime.test.ts` (auth header construction, custom prefix, pathPrefix, query params, missing-connector failure for writes, HTTP error reporting).

## Custom tool format and the `.simple-harmonic/skills/` data directory

### Loader contract (`packages/backend/src/server/custom-tools.ts`)

A custom tool is a **flat JSON file** at `.simple-harmonic/skills/<name>.json` (resolved against `toolsRoot()`, `custom-tools.ts:27,35-37`). ### Registry: Pydantic args models, JSON-Schema inlining, structured failures

`ToolDefinition` (`tools/registry.py`) carries the same fields as its TS counterpart — `name`, `description`, `category`, `risk`, an optional argument-aware `is_destructive` classifier — but `schema` is a `pydantic.BaseModel` subclass instead of a Zod schema. The registry uses it for both validation and LLM-facing schema generation: `schema_to_parameters()` calls `model_json_schema()`, pops the `$schema` meta key (which the LLM APIs reject), and **inlines all `$defs`** via `_inline_refs()` because OpenAI/Anthropic tool-parameter blocks don't carry a definitions section, so nested models (e.g. a custom tool's `query` object) must be flattened in place — a wrinkle Zod's `zod-to-json-schema` handled differently. `ToolRegistry.execute()` (`registry.py:159`) preserves the never-raise contract: a missing tool or a `ValidationError` is caught and returned as a `ToolExecResult(success=False, …)` with a flattened `loc: msg` issue string for self-correction, never an exception. `register()` still raises on a duplicate name (`registry.py:107`), and `is_destructive()` (`registry.py:142`) still fail-safes — **unknown tool ⇒ destructive** (risk-register item 19), and an args model that won't `model_validate` is also treated as destructive. `create_app_registry()` / `create_app_registry_with_custom_tools()` (`tools/index.py`) register the identical 12 app tools in the identical order on top of `create_default_registry()`'s three internal tools, and the custom-tool loop swallows failures with the same whole-loop `try/except` (`index.py:73-81`) — so the same nuance applies: one custom tool whose def construction throws drops every not-yet-registered custom tool, not just itself.

### Filesystem jail and env scrub (`tools/sandbox.py`)

The jail primitives port directly. `tools_root()` reads `SH_TOOLS_CWD or os.getcwd()` **at call time** (not through the cached `Settings` object) precisely so a stale root can never become a containment bug — the module docstring calls this out explicitly. `resolve_in_jail()` is the synchronous logical check (rejects null bytes, absolute paths, `..`); `resolve_in_jail_real()` is the **async** symlink-aware check used by both filesystem tools — it realpaths the jail root (so a `/tmp` → `/private/tmp` macOS symlink compares correctly) and realpaths the deepest *existing* ancestor via `_realpath_deepest_existing()`, re-appending the non-existent tail (which can't itself be a symlink). A symlink inside the jail pointing out is rejected, not followed (risk-register: symlink jail). The one idiomatic shift: the TS `realpathDeepestExisting` walk becomes a `Path`-based loop using `os.lstat` for an lstat-style existence probe that doesn't follow a final symlink.

`scrubbed_env()` (`sandbox.py:120`) is the same hard allowlist — `PATH, HOME, USER, SHELL, LANG, LC_ALL, TMPDIR, TZ` — and every other variable (`*_API_KEY`, `GITHUB_TOKEN`, `APOLLO_MASTER_KEY`, and any DB URL) is dropped; this is a security guarantee, not an optimization (risk-register item 12). `coding_env(extra_keys)` adds only the named provider keys that match `_ENV_KEY_RE = ^[A-Z][A-Z0-9_]*$`; a lowercase or malformed key name is silently ignored. `tools_enabled()` (`sandbox.py:46`) is the **kill switch**: true only when `SH_ENABLE_TOOLS ∈ {1, true, yes}` (case-insensitive), default OFF (risk-register item 11). `write_file`, `run_command`, `coding_task`, and mutating `github_api`/custom-API calls each check it in their own impls, so the gate applies identically regardless of runtime.

`read_file` (`tools/filesystem.py:95`) keeps the read-only sensitive-path denylist (`_is_sensitive_path`, `filesystem.py:77`): `.simple-harmonic/secrets.json`, anything under `.apollo/`, any `.env*` basename that isn't `.example`/`.sample`/`.template`, `.npmrc`/`.pypirc`/`.netrc`, the `id_rsa`/`id_dsa`/`id_ecdsa`/`id_ed25519` key files, any `*.pem`/`*.key`, and any `.ssh` component — applied to the jail-relative path, case-insensitive, and **only to `read_file`**; `write_file` (`filesystem.py:154`) performs no sensitive-path check, so with the kill switch on it can still overwrite a jailed `.env`. The 256 KiB read cap and the friendly error mapping (`JailEscapeError` → its message, `FileNotFoundError` → "File not found", `PermissionError` → "Permission denied", `IsADirectoryError` → "Path is a directory") survive; blocking `os.stat`/`read_text`/`write_text` calls are dispatched through `asyncio.to_thread` so they never block the event loop.

### Shell-free `run_command` (`tools/shell.py`)

The defining property is preserved exactly: the child is spawned with `asyncio.create_subprocess_exec(program, *argv, …)` — a **literal argv, never a shell** — so `|`, `;`, `&&`, `$(...)`, backticks, and `>` are inert literal tokens (risk-register item 10). The same 23-program `ALLOWED_PROGRAMS` frozenset (interpreters like `node`/`python` deliberately absent), the same `_is_escaping_arg` screen (null bytes, absolute paths, `~`/`~/`, any `..` traversal form, and the `--git-dir=`/`--work-tree=`/`--output=`/`--exec-path=` git-redirection flags via `_ESCAPING_FLAG_RE`), and the same `ALLOWED_GIT_SUBCOMMANDS` allowlist (read-only plus write subcommands, permitted because `run_command` is itself approval-gated) are checked in the same order. Runtime limits match: `cwd` pinned to `tools_root()`, env `scrubbed_env()`, a 30 s timeout (`asyncio.wait_for` → `proc.kill()` on `TimeoutError`, reported as `…after 30000ms`), 64 KiB output cap, stderr appended under a `[stderr]` marker, non-zero exit returned as a failure.

### SSRF egress guard (`tools/url_guard.py`) and the IPv4-pinned proxy fetch (`proxy_fetch.py`)

This is the most safety-critical pair, and the port treats it as such. `assert_public_and_resolve()` (`url_guard.py:124`) is the single egress policy for every agent-driven outbound request and is `async` so it can resolve DNS via the event loop (`loop.getaddrinfo`, the overridable `_resolve_all` seam tests patch to run fully offline). It rejects: any non-`https:` scheme; URLs with embedded credentials; `localhost`/`*.localhost` (after lowercasing, stripping a trailing dot, and stripping IPv6 brackets); IP-literal hosts in private ranges with no DNS lookup; DNS names where **any** resolved address is private (a mixed public+private record set is rejected wholesale, defeating a poisoned rebind set); and DNS failures / empty record sets.

The private ranges are **test-pinned** and replicated exactly (risk-register item 9). `is_private_ipv4()` (`url_guard.py:40`) covers `0.*`, `10.*`, `127.*`, CGNAT `100.64–127.*`, link-local/metadata `169.254.*`, `172.16–31.*`, `192.168.*`, benchmark `198.18–19.*`, and everything `>= 224.*`; `is_private_ipv6()` covers `::1`, `::`, `fc`/`fd` ULA, `fe80` link-local, and `::ffff:`-mapped v4. On success it returns a `PinnedTarget` carrying a pre-resolved public IP (preferring IPv4) — the anti-rebinding pin.

The **SSRF-before-token order** is load-bearing and preserved at all three call sites (risk-register item 8): in `http_fetch` and `github_api` (`tools/network.py`), and in the custom-API impl (`tools/api_tool_runtime.py`), `assert_public_and_resolve` runs and *passes* before any `Authorization`/connector header is built and before `proxy_fetch` is called. In `github_api_impl` (`network.py:162-164`) the guard runs, *then* the `Bearer <token>` header is attached; in `build_api_tool_impl` (`api_tool_runtime.py:107-127`) the guard runs, *then* `resolve_connector` value is placed into the auth header — so a skill whose `baseUrl` resolves to an internal or metadata host fails at the guard and the bearer token never leaves the box. The module docstrings on both `network.py` and `api_tool_runtime.py` flag this ordering as deliberate.

`proxy_fetch.py` is where the port's verifier caught and fixed two real bugs that a naive translation would have introduced (called out in MIGRATION.md slice 6). Both stem from httpx not being `https.request`:

- **SNI/cert pin.** The TS `pinnedLookup` overrides only DNS while keeping the hostname for TLS SNI and certificate verification. The naive httpx approach — rewriting the URL to the bare pinned IP — would make SNI and cert validation target the IP and fail for every real HTTPS host. `_PinnedTransport` (`proxy_fetch.py:157`) instead dials `pin.ip` at the httpcore layer while leaving the request URL host, the `Host` header, and the TLS `server_hostname` (set explicitly via the `sni_hostname` extension) pointed at the real hostname. This closes the DNS-rebinding TOCTOU without weakening cert checks — the load-bearing fidelity behavior.
- **Streaming byte cap.** `proxy_fetch()` returns a **streaming** `httpx.Response` whose body is not yet read; `read_capped()` (`proxy_fetch.py:274`) consumes it lazily via `aiter_bytes()` and **breaks the moment the cap is hit**, so a malicious server cannot stream an unbounded body into memory. The client is stashed on the response (`_pinned_client`) and torn down in `read_capped`'s `finally`, even on early stop. The 128 KiB body cap (`http_fetch`, `github_api`, custom tools) and 20 s timeout (`FETCH_TIMEOUT_S`) match the TS values.

The **IPv4 pin** (risk-register item 17) is preserved to dodge hanging IPv6/Teredo tunnels: `_build_client()` binds an IPv4 local address (`0.0.0.0`) for the no-pin and v4-pin cases, while a v6 pin is allowed to bind v6 — the Python equivalent of the TS `family: pin?.family ?? 4`. The proxy decision (`build_plan()`) honors `HTTPS_PROXY`/`HTTP_PROXY` (and lowercase variants), falls back to the cached macOS system proxy (`scutil --proxy`), and — importantly — **drops the pin on the proxy path** because the proxy is itself a trust boundary that resolves the host. `build_plan` is a pure function the tests assert on without opening a socket.

### Connectors and custom HTTP skill tools

`resolve_connector()` (`connectors.py:59`) keeps the resolution order **`.simple-harmonic/secrets.json` first, then `os.environ`** (never a DB). `custom_tools.py` reads the same flat `.simple-harmonic/skills/<name>.json` files (`{ name, description, config: ApiToolConfig }`), skipping entries without a truthy `name` or `config.baseUrl` and silently skipping malformed JSON; `ApiToolConfig` lives in `store/types.py` as a shared Pydantic model with the same fields (`baseUrl`, `connectorKey`, `authHeader?`, `authPrefix?`, `allowedMethods`, `defaultHeaders?`, `pathPrefix?`). Tool-name validation against path traversal uses `TOOL_NAME_RE = ^[A-Za-z][A-Za-z0-9_-]*$` (`validation.py`). The custom-tool def (`build_api_tool_def`) is built with Pydantic's `create_model()` so the method enum is a `Literal[tuple(allowedMethods)]` (falling back to `["GET"]` when empty), and risk is the same argument-aware `method != "GET"` classifier — GET runs unapproved, writes gate. The impl mirrors the TS step order: resolve connector (missing connector fails non-GET only), build `baseUrl + pathPrefix + path` with query params, **SSRF guard**, build headers (`User-Agent`, `defaultHeaders`, then the auth header with `authPrefix` default `Bearer` and an explicit empty-string prefix sending the raw value, then `Content-Type` when a body is present), then `proxy_fetch` with the pin and 128 KiB cap, emitting `api_tool_called`.

### Coding subsystem (`tools/coding/`)

The unified `coding_task` tool ports faithfully (`coding/index.py`): category `shell`, risk `destructive`, gated by `tools_enabled()`. Backend selection resolves through `get_config().codingBackend` (file `codingBackend` → `SH_CODING_BACKEND` env → default `"codex"`, validated against `codex | claude-code | opencode` with invalid names falling back to codex), and `create_coding_backend()` raises on an unknown name (fail loud). `build_summary()` produces the same errors/commands/conclusion layout (4,000-char conclusion cap; first 5 output lines per command), and the call is reported as failure only when there are errors **and** zero messages. The shared `run_subprocess()` (`coding/run_subprocess.py`) single-sources the security posture: the cwd is re-validated through `resolve_in_jail` before spawn, the child runs via `asyncio.create_subprocess_exec` (shell-free) with `env=coding_env(env_keys)` (scrubbed base plus only the named provider keys), `stdin` is `DEVNULL`, a timeout `kill()`s the child and **returns the partial parse plus a `Timed out after Ns` error** (never raises), stdout is capped keeping the tail trimmed to a line boundary so a JSONL record is never cut mid-line, and stderr is capped at 8,192 bytes. The three adapters differ only in argv and forwarded env keys — `claude-code` (`ANTHROPIC_API_KEY`, with `--dangerously-skip-permissions --no-session-persistence`), `codex` (`CODEX_HOME`, `OPENAI_API_KEY`; `-s workspace-write --skip-git-repo-check`), `opencode` (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) — each with a 5-minute default timeout and a 256 KiB stdout cap; there is no session/resume in this subsystem.

### Async and the store lock as they apply here

The chapter's subsystem is mostly stateless I/O, so the broad asyncio shift (risk-register item 1, the `asyncio.Lock` around every store read-modify-write) surfaces in the tools layer only where tools write through the store repos — the four **management tools** (`set_team_goal`, `spawn_sub_team`, `modify_agent`, `modify_team` in `tools/management.py`) and `action_history`'s reads. Those go through the same locked repo methods the rest of the backend uses (`agents`, `teams`, `actionLog`), so a tool mutation and a concurrent tick can't interleave a read-modify-write. The tools themselves are otherwise pure async functions whose blocking work (filesystem stats/reads/writes, subprocess waits, DNS) is dispatched via `asyncio.to_thread` or native async APIs (`create_subprocess_exec`, httpx's async transport).

### Deferred / known divergences relevant to this chapter

This subsystem ports cleanly; the only chapter-adjacent divergences are documented in MIGRATION.md and live one layer up, in how a destructive tool call is *acted on* rather than how it is *classified*:

- **The per-call approval gate** still relies on `registry.is_destructive` exactly as described above — the classifier is fully ported and the kill switch is enforced inside each impl. But the **codex app-server harness resume path is not ported**: a parked `codex-thread` tick resumes through the legacy runner, and `use_codex_harness` is computed/stored for parity but unread in the resume path. The legacy-runner round-atomic suspend/resume (the HOLD/resume/deny trichotomy that parks destructive tool calls as approval records) is fully ported and tested.
- The skills-directory migration parked in `stash@{0}` is equally absent from the Python port — the built-in count is **15**, there is no SKILL.md loader, no skill tree, and no open-skill runner state, matching `main`.

For the full stack rationale (raw SDKs + asyncio, Pydantic v2 replacing Zod, the store lock) and the complete fidelity risk register, see [`backend-py/ARCHITECTURE.md`](../backend-py/ARCHITECTURE.md); for the slice-by-slice status (this subsystem is slice 6, 576 tests at that point) see [`backend-py/MIGRATION.md`](../backend-py/MIGRATION.md).
