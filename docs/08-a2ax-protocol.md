# 08 — A2AX Protocol (`packages/a2ax`)

`@simple-harmonic/a2ax` v0.1.0 ("A2A-Extended") is the agent-to-agent communication library of the monorepo: a storage-agnostic protocol class (`A2AX`) layered over a `Transport` interface, with two transport implementations (in-memory and a JSON-file adapter) and a type system covering messages, channels (direct/broadcast/group/task), tasks with a validated state machine, A2A-style agent cards, and scoped bearer tokens. The host app instantiates it once as a singleton over `JsonFileTransport` (`packages/backend/src/server/a2ax.ts`) and uses it as the message bus between agents during scheduler ticks; a substantial part of the library's surface (groups lifecycle, agent cards, auth tokens, message expiry) is implemented and tested but not exercised by any host code. PR #16 replaced the previous Postgres transport: there is no longer a Drizzle adapter, no `a2ax_*` tables, and no SQL — each team's communication state lives in plain files under that team's folder in the data tree, and the read-side dashboard routes now read through the protocol/transport rather than querying tables directly.

## 1. Purpose and position

The package models team-scoped agent communication. Everything is keyed by `teamId`; agents are referenced only by ID strings (the package has no notion of an agent record — agent identity lives in the host's file store under `agent.json`, plus sentinel UUIDs for the human cofounder/user defined in `packages/backend/src/lib/meta-agent/identity.ts`). Four channel types exist (`packages/a2ax/src/types/message.ts:6`):

| Channel type | Semantics | Channel ID scheme (`packages/a2ax/src/types/channel.ts:29-47`) |
|---|---|---|
| `direct` | 1:1 between two agents | `direct:<idA>:<idB>` — the two agent IDs lexicographically sorted, so the channel is deterministic regardless of sender |
| `broadcast` | One-to-all within a team | `team:<teamId>` |
| `group` | Explicit membership list | `group:<uuid>` |
| `task` | Per-task thread | `task:<taskId>` |

The public entry point `packages/a2ax/src/index.ts` re-exports the `A2AX` class, `A2AXOptions`, `AgentContext`, `MessageQuery`, `Transport`, and everything in `src/types/` (`export *` of `agent-card.ts`, `auth.ts`, `channel.ts`, `message.ts`, `task.ts`).

## 2. Domain model — exact type shapes

### 2.1 Message (`packages/a2ax/src/types/message.ts`)

| Field | Type | Notes |
|---|---|---|
| `id` | `string` | UUID, generated by the transport |
| `teamId` | `string` | required |
| `channelType` | `"direct" \| "broadcast" \| "group" \| "task"` | |
| `channelId` | `string` | see ID schemes above |
| `fromAgentId` | `string` | |
| `role` | `"agent" \| "meta" \| "system" \| "user"` (`MessageRole`) | defaults to `"agent"` in both transports |
| `kind` | `MessageKind` | union of `GeneralKind` (`text`, `data`, `artifact`, `ack`, `error`), `TaskKind` (`task.create`, `task.accept`, `task.status`, `task.input_required`, `task.result`, `task.cancel`, `task.reject`), `SystemKind` (`system.join`, `system.leave`, `system.created`) |
| `content` | `string` | primary text body |
| `parts?` | `Part[]` | A2A-compatible content units |
| `artifacts?` | `Artifact[]` | named collections of output parts |
| `payload?` | `Record<string, unknown>` | structured side data |
| `replyTo?` | `string` | message ID for threading |
| `status` | `"pending" \| "delivered" \| "read" \| "expired"` (`MessageStatus`) | transports only ever set `pending` (default) and `expired`; `delivered`/`read` are never assigned by any code (per-recipient reads are tracked separately, see §4) |
| `urgent?` | `boolean` | stored and rendered by the frontend (ring/badge in `packages/frontend/src/components/team/agent-messages-view.tsx:717`, `agent-pov-view.tsx:815`); no scheduling logic reads it |
| `expiresAt?` | `Date \| null` | |
| `createdAt` | `Date` | |

`Part` (`packages/a2ax/src/types/message.ts:34`): `{ text?, raw?, url?, data?, mediaType?, filename?, metadata? }` — exactly one content field is expected. `Artifact` (`:47`): `{ artifactId, name?, description?, parts: Part[], metadata? }`. `CreateMessageInput` (`:84`) mirrors `Message` minus `id`/`status`/`createdAt`, with `role` optional.

### 2.2 Channel (`packages/a2ax/src/types/channel.ts`)

`Channel`: `{ id, teamId, channelType, name?, metadata?, createdAt }`. `ChannelMember`: `{ channelId, agentId, joinedAt }` — membership only matters for `group` channels.

### 2.3 Task (`packages/a2ax/src/types/task.ts`)

`Task`: `{ id, teamId, channelId, requestorId, assigneeId, title, description, state, metadata?, createdAt, updatedAt }`. `TaskState` is A2A-compatible: `submitted | accepted | working | input_required | completed | failed | canceled | rejected`. The transition table `TASK_TRANSITIONS` (`packages/a2ax/src/types/task.ts:48`):

| From | Allowed to |
|---|---|
| `submitted` | `accepted`, `rejected`, `canceled` |
| `accepted` | `working`, `canceled` |
| `working` | `input_required`, `completed`, `failed`, `canceled` |
| `input_required` | `working`, `canceled` |
| `completed`, `failed`, `canceled`, `rejected` | (terminal — no transitions) |

`isValidTransition(from, to)` (`:60`) is a lookup into that table. `CreateTaskInput`: `{ teamId, requestorId, assigneeId, title, description, metadata? }`. `UpdateTaskInput`: `{ state?, metadata? }`.

### 2.4 Agent card (`packages/a2ax/src/types/agent-card.ts`)

`AgentCard` (`:75`): `{ id, name, description?, provider?, endpoint, capabilities, skills, securitySchemes?, security?, signature?, metadata? }`.

- `AgentCapabilities` (`:6`): `{ streaming, pushNotifications, extendedAgentCard: boolean }` plus a2ax extensions `broadcast?`, `groups?`, `tasks?`.
- `AgentSkill` (`:19`): `{ id, name, description?, inputSchema?, outputSchema?, acceptedMediaTypes? }`.
- `AgentProvider` (`:29`): `{ name, url?, contact? }`.
- `SecurityScheme` (`:36`): OpenAPI-style discriminated record (`apiKey | http | oauth2 | openIdConnect | mutualTls`) with `OAuthFlows`/`OAuthFlow` for the oauth2 case.
- `AgentCardSignature` (`:68`): `{ algorithm, signature, keyId? }`.
- `createAgentCard(opts)` (`:90`) fills defaults: `streaming/pushNotifications/extendedAgentCard: false`, `broadcast/groups/tasks: true`, `skills: []`, then spreads `opts`.

Team scoping of cards is by convention: `teamId` is stored inside `metadata` (both transports filter `metadata.teamId === teamId` in `listCards`).

### 2.5 Auth (`packages/a2ax/src/types/auth.ts`)

`AgentToken`: `{ agentId, teamId, token, scopes: string[], expiresAt?, createdAt }`. `Scope` is a 13-member union: `message:send`, `message:read`, `task:create`, `task:update`, `task:cancel`, `broadcast:send`, `group:join`, `group:leave`, `group:send`, `group:create`, `card:read`, `card:write`, `admin`. `DEFAULT_SCOPES` (`:16`) is the 8-scope subset granted by default (everything except `task:cancel`, `group:leave`, `group:create`, `card:write`, `admin`). `hasScope` (`:44`) returns true if the token has the scope or `admin`. `generateToken` (`:49`) returns 32 random bytes hex-encoded (64 chars) via `crypto.getRandomValues`.

## 3. The protocol core: class `A2AX` (`packages/a2ax/src/core/protocol.ts`)

Constructor (`:54`): takes `A2AXOptions { transport, maxContextMessages?, defaultExpiryMs? }`; defaults are 20 messages and 7 days (`604800000` ms).

| Method | Parameters | Validation | Side effects | Returns / errors |
|---|---|---|---|---|
| `sendDirect` (`:64`) | `teamId, fromAgentId, toAgentId, content, opts?{kind, parts, payload, urgent}` | none | ensures the deterministic direct channel exists, inserts a message with `expiresAt = now + defaultExpiryMs` | `Message` |
| `broadcast` (`:99`) | `teamId, fromAgentId, content, opts?{kind, parts, payload}` | none | ensures channel `team:<teamId>` (named `"team-broadcast"`), inserts message with default expiry | `Message` |
| `createGroup` (`:130`) | `teamId, name, memberIds[]` | none | creates channel `group:<uuid>`, adds each member, inserts a `system.created` message (role `system`) attributed to `memberIds[0]` | `{ channelId }` |

| `getAgentContext` (`:294`) | `teamId, agentId` | none | none (read-only) | `AgentContext { messages, formatted, messageIds }` |

`listMessages` and `listTasks` are the read-view methods added in PR #16 so the dashboard routes (§5.3) can read team-wide history through the protocol instead of touching storage directly.

### `getAgentContext` mechanics (`:294-347`)

Runs four sequential `queryMessages` calls — one per channel type (`direct`, `broadcast`, `group`, `task`), each with `unreadOnly: true` and `limit: maxContextMessages` — concatenates, sorts ascending by `createdAt`, and slices to `maxContextMessages`. Because the sort is ascending and the slice keeps the head, truncation keeps the **oldest** unread messages and drops the newest. `formatted` (`formatContext`, `:459`) is empty string when there are no messages; otherwise a block of the form:

```
--- Messages since last tick ---

[direct from <agentId>]:
<content>

...
---
```

Prefixes per channel type (`formatPrefix`, `:470`): `[direct from X]:`, `[broadcast from X]:`, `[<channelId> from X]:` for groups, `[<channelId> from X] (<kind>):` for tasks.

`ensureChannel` (`:442`) is get-then-create. Under the JSON-file transport this is harmless: all transport IO is synchronous and the host is single-process/single-writer, so a get-then-create runs to completion within one event-loop task and cannot interleave with another tick's mutation; a duplicate `createChannel` would simply overwrite the same `channels.json` entry (last write wins) rather than raising a constraint error.

## 4. Transport abstraction

### 4.1 The `Transport` interface (`packages/a2ax/src/core/transport.ts:27`)

Twenty-two methods across five groups (5 messages + 7 channels + 4 tasks + 3 cards + 3 auth); `MessageQuery` (`:12`) is `{ teamId, agentId, unreadOnly?, limit?, channelType? }`.

| Group | Methods |
|---|---|
| Messages | `insertMessage(input)`, `queryMessages(query)`, `listTeamMessages(teamId, limit?)` (all team messages, chronological, **not** relevance-filtered — added in PR #16 for the dashboard views), `markRead(agentId, messageIds)` (per-recipient, not global), `markExpired(before): Promise<number>` |
| Channels | `getChannel`, `createChannel(Omit<Channel,"createdAt">)`, `listChannels(teamId)`, `addMember`, `removeMember`, `getMembers(channelId)`, `getMemberships(agentId)` |
| Tasks | `createTask`, `getTask`, `updateTask`, `listTasks(teamId, agentId?)` |
| Agent cards | `getCard`, `upsertCard`, `listCards(teamId)` |
| Auth | `createToken`, `getToken`, `revokeToken` |

The protocol class now calls `listTeamMessages` (via `listMessages`) and `listTasks` (via its own `listTasks`) for the read views. It still never calls `listChannels`, `getMembers`, or `revokeToken` — those exist only for direct transport consumers (none in the host today).

### 4.2 `MemoryTransport` (`packages/a2ax/src/transport/memory.ts`)

Plain in-process structures: `messages: Message[]`, `reads: Set<string>` keyed `` `${messageId}:${agentId}` `` (per-recipient read tracking — a broadcast/group message is one row, so reads must be per-agent), `channels: Map`, `members: ChannelMember[]`, `tasks: Map`, `cards: Map`, `tokens: Map`.

`queryMessages` (`:50`) filters by team, then (if `unreadOnly`) excludes `expired` messages and ones in the agent's read set, then by `channelType`, then applies **relevance** (`:66-96`): own messages are always excluded; `direct` requires `channelId === directChannelId(querier, sender)`; `broadcast` always matches; `group` requires membership; `task` requires the querier to be requestor or assignee of the task whose channel matches. Results sort ascending by `createdAt` and are head-sliced by `limit`.

Other notes: `addMember` (`:140`) deduplicates (returns the existing membership); `createTask` (`:166`) generates the ID then rewrites `channelId` to `task:<taskId>`; `updateTask` (`:190`) merges `metadata` shallowly and throws on missing task; `listCards` (`:220`) filters strictly on `metadata.teamId === teamId`. `listTeamMessages` (`:107`) returns every team message sorted ascending by `createdAt`, head-sliced by `limit` — no relevance filter, no read filter.

### 4.3 `JsonFileTransport` (`packages/a2ax/src/adapters/json-file.ts`)

The production transport since PR #16. It implements the same `Transport` interface as `MemoryTransport` and reuses the **identical** relevance logic, but persists each team's communication state to plain files under that team's folder in the recursive data tree. Constructed with the absolute path to `<dataDir>/teams` (`constructor(private teamsRoot: string)`, `:58`).

**On-disk layout** (header comment, `:4-11`) — per team, under `<teamDir>/messages/`:

| File | Format | Contents | Written by |
|---|---|---|---|
| `log.jsonl` | JSONL (append) | one message per line; rewritten wholesale only on bulk expiry | `insertMessage` (append), `markExpired` (rewrite) |
| `reads.jsonl` | JSONL (append) | per-recipient read receipts `{messageId, agentId, readAt}` | `markRead` |
| `channels.json` | JSON array | the team's channels | `createChannel` |
| `members.json` | JSON array | group memberships scoped to the team's channels | `addMember`/`removeMember` |
| `tasks.json` | JSON array | the team's tasks | `createTask`/`updateTask` |
| `cards.json` | JSON array | agent cards whose `metadata.teamId` matches | `upsertCard` |
| `tokens.json` | JSON array | the team's tokens | `createToken`/`revokeToken` |

There are no tables, no enums, and no SQL: the row shapes are the public TypeScript types from `src/types/` written verbatim as JSON (dates as ISO strings).

**In-memory + write-through model.** The adapter keeps the full state in process memory — `messages: Message[]`, `reads: Set<string>` keyed `` `${messageId}:${agentId}` ``, `channels: Map`, `members: ChannelMember[]`, `tasks: Map`, `cards: Map`, `tokens: Map` (`:45-51`) — mirroring `MemoryTransport`'s structures exactly. State is hydrated lazily, once, on the first transport call (`hydrate`, `:62`): it calls `discoverTeamMessageDirs(teamsRoot)` (the recursive team-tree walk in `file-store.ts`, §4.4) to build a `teamId → messages-dir` map, then reads every team's files into memory (`loadDir`, `:69`), reviving `createdAt`/`expiresAt`/`joinedAt`/`updatedAt` strings back to `Date`. Holding everything in memory is what lets the `teamId`-less methods (`markRead`, `getTask`, `getToken`, `getCard`, `getMembers`, …) resolve in O(1) without re-reading from disk. Every mutation updates the in-memory structure **and** writes through to the owning team's file: object collections are rewritten atomically (`persistChannels`/`persistMembers`/`persistTasks`/`persistCards`/`persistTokens`, `:117-152`, each filters the in-memory collection down to the one team before `writeJson`), while `log.jsonl` and `reads.jsonl` are appended one line at a time. If a team folder appears after hydration, `dirForTeam` (`:104`) re-walks the tree once to find it (and throws `a2ax: team ${teamId} folder not found` if it still cannot — the team's folder must exist on disk before any a2ax call for that team).

**Op-by-op behavior** (note how each parallels the memory transport):

- `insertMessage` (`:156`): builds the `Message` (UUID id, `role` defaulting to `"agent"`, `status: "pending"`, `expiresAt` defaulting to `null`, `createdAt: new Date()`), pushes it to memory, and `appendJsonl`s it to the team's `log.jsonl`.
- `queryMessages` (`:181`): byte-for-byte the same filter + relevance pipeline as `MemoryTransport` (team match → optional unread/`!expired` filter → optional `channelType` → relevance: own-excluded, `direct` by `directChannelId`, `broadcast` always, `group` by membership, `task` by requestor/assignee), then sort ascending by `createdAt` and head-slice by `limit`. Because it filters the full in-memory array *before* slicing, the limit always returns relevant rows (unlike the old Drizzle adapter, which sliced in SQL before the JS relevance filter and could starve a busy team's context window).
- `listTeamMessages` (`:225`): all of a team's messages sorted ascending by `createdAt`, head-sliced by `limit` — no relevance/read filter; powers the dashboard views (§5.3).
- `markRead` (`:233`): for each new `${id}:${agentId}` key, adds it to the `reads` set and appends `{messageId, agentId, readAt}` to that message's team's `reads.jsonl`; already-read keys are skipped (no duplicate append).
- `markExpired` (`:250`): flips `status` to `"expired"` on every in-memory message past `before`, then **rewrites** `log.jsonl` (via `rewriteJsonl`) for each affected team so the status change is durable.
- `addMember` (`:290`): deduplicates like the memory transport (returns the existing membership) — there is no constraint-free duplicate path the way the old Drizzle adapter had.
- `createTask` (`:322`): generates the UUID, sets `channelId = task:<id>` and `state: "submitted"`, persists `tasks.json`.
- `updateTask` (`:349`): throws `Task ${taskId} not found`; sets `state` if given; **merges** `metadata` (`{ ...task.metadata, ...input.metadata }`) — matching the memory transport (the old Drizzle adapter replaced it); always bumps `updatedAt`; rewrites `tasks.json`.
- `upsertCard` (`:376`): sets the card in memory; persists `cards.json` only when `metadata.teamId` is a string (cards without a team scope are held in memory but not written).
- `listCards` (`:384`): filters strictly on `metadata.teamId === teamId`.

The opaque JSON blobs (`parts`, `artifacts`, `payload`, `metadata`) round-trip as-is; only the declared top-level date fields are revived, so nested ISO-looking strings inside those blobs are never coerced.

### 4.4 The package's own fs helpers (`packages/a2ax/src/storage/file-store.ts`)

`JsonFileTransport` does not import the backend's store. The a2ax package is a standalone library with no dependency on `@simple-harmonic/backend`, so it ships its own minimal, self-contained synchronous fs helpers (header comment, `:1-7`) that mirror the backend's primitives:

- `readJson<T>(path, fallback)` (`:24`): reads + parses, returning `fallback` on `ENOENT` or an empty file.
- `writeJson(path, value)` (`:35`): atomic write — `JSON.stringify(value, null, 2)` to `<path>.tmp`, then `renameSync` over the target (creating the parent dir first via `ensureDir`).
- `readJsonl<T>(path)` (`:42`): parses one JSON object per non-blank line, `[]` on `ENOENT`.
- `appendJsonl(path, row)` (`:58`): appends one stringified line.
- `rewriteJsonl(path, rows)` (`:63`): atomic full rewrite (temp + rename), used by `markExpired`.
- `discoverTeamMessageDirs(teamsRoot)` (`:86`): the recursive team-tree walk — a folder is a team if it contains `team.json`; its sub-teams live in its `teams/` subfolder, recursed into. Returns `teamId → <teamDir>/messages`. This is the function `hydrate`/`dirForTeam` use to locate every team's files; sub-team nesting on disk is why a `teamId` is not derivable from a fixed path and must be indexed by this walk.

These are deliberate near-duplicates of the backend store's fs-store primitives (atomic JSON, JSONL append, temp+rename). Keeping them inside the package is what preserves the protocol library's storage independence: any consumer can use `JsonFileTransport` by pointing it at a directory tree, with no coupling to the host application's store module.

## 5. Backend wiring and actual usage

### 5.1 The singleton (`packages/backend/src/server/a2ax.ts`)

`getA2AX()` (`:11`) lazily constructs one process-wide `A2AX` over `new JsonFileTransport(teamsRoot())` with `maxContextMessages: 20` and `defaultExpiryMs` of 7 days, then memoizes it (`teamsRoot()` comes from `./store/data-dir` and resolves to `<dataDir>/teams`). The JSON-file adapter is the **only transport used in production**; `MemoryTransport` is used solely by the package's own tests. PR #16 also added `resetA2AXForTests()` (`:27`), which drops the cached instance so tests that repoint `SH_DATA_DIR` between cases get a fresh transport over the new directory. Unlike the old Drizzle singleton, the transport captures the teams root path at construction, so the cached instance must be reset when the data dir moves. The backend a2ax behavior is pinned by `packages/backend/tests/unit/a2ax.test.ts`, which exercises the **real** `JsonFileTransport` over a temp store (`useTempStore()`): it asserts the singleton identity, then seeds a team via `teams.insert()` (the team's on-disk folder must exist before any a2ax call) and round-trips direct/broadcast messages and tasks through `a2ax.listMessages`/`getAgentContext`/`listTasks`.

### 5.2 Write path — protocol methods the app actually calls

- **Tick scheduler** `packages/backend/src/server/api/tick.ts`: per fresh agent run (`runFreshAgent`) it calls `a2ax.getAgentContext(team.id, agent.id)` (`:401`), injects `ctx.formatted` into the shared run config as `a2axContext` (`:425`) — both engines consume it: `buildTickPrompt` (`packages/backend/src/lib/meta-agent/runner.ts:607`) appends it to the tick prompt at `runner.ts:628-629`, and the codex app-server harness reuses the same builder for its turn input (`codex-harness.ts:239`) — passes the live `a2ax` instance into the config (`tick.ts:434`; the codex harness hands it to its dynamic-tool context at `codex-harness.ts:147`), and after a successful run calls `a2ax.markContextRead(agent.id, ctx.messageIds)` (`:462`). Resumed runs (`tryResumeAgent`, `:485`) skip the context fetch. On agent failure, `failAgent` (`:630`) fire-and-forgets `a2ax.broadcast(teamId, agent.id, "[SYSTEM] Agent ... errored ...", { kind: "text", payload: { systemAlert: true, ... } })` (`:660-664`) so peers see the failure on their next tick.
- **Agent tools** `packages/backend/src/lib/meta-agent/default-tools.ts`: the built-in `send_message` tool calls `ctx.a2ax.sendDirect` (`:69`) after resolving the peer by name, and the `broadcast` tool calls `ctx.a2ax.broadcast` (`:92`). The meta-agent library depends only on the structural type `A2AXSender` (`packages/backend/src/lib/meta-agent/tools.ts:56`), which is just `{ sendDirect, broadcast }` — keeping the library free of a concrete a2ax dependency; the tick handler supplies the real instance.
- **Messages API** `packages/backend/src/server/api/team/id/messages.ts`: GET calls `getAgentContext` (`:23`) and returns name-enriched messages (without marking them read); POST translates cofounder/user POV sentinels to their agent UUIDs (`:71-76`), then dispatches on `channelType` to `broadcast` (`:87`), `sendToGroup` (`:96`, requires `channelId`), or `sendDirect` (`:105`, the default, requires `toAgentId`).
- **Seed route** `packages/backend/src/server/api/seed.ts`: demo data via many `sendDirect` calls, two `broadcast`s, nine `createTask`s, and a series of `updateTaskState` calls walking real lifecycles.

So the exercised protocol surface is exactly: `sendDirect`, `broadcast`, `sendToGroup`, `createTask`, `updateTaskState`, `getAgentContext`, `markContextRead`.

### 5.3 Read path — the dashboards read through the protocol

PR #16 removed the host's duplicate Drizzle schema and the raw-SQL reads. The three read-side dashboard routes now go through `getA2AX()` and the new `listMessages`/`listTasks` protocol methods (which delegate to the transport's `listTeamMessages`/`listTasks`), so they read the **same** in-memory/file-backed state the write path produces — there is no separate query layer:

- `packages/backend/src/server/api/team/id/conversations.ts:36` calls `a2ax.listMessages(teamId, 1000)` and `a2ax.listTasks(teamId)` (`:52`), then groups messages into conversation threads in JS and resolves task titles for `task:` channels.
- `packages/backend/src/server/api/team/id/tasks.ts:35` calls `a2ax.listTasks(teamId, …)` (team- or participant-scoped), sorts by `updatedAt`, slices to 200.
- `packages/backend/src/server/api/team/id/agent-hub.ts:28` calls `a2ax.listMessages(teamId, 200)` alongside the store reads for agents and the action log.

Team-name enrichment, POV-sentinel translation, and participant filtering all happen in the route in JS, against the rows the protocol returns. (The store's domain repos — `teams`, `agents`, `actionLog` from `packages/backend/src/server/store` — supply the non-a2ax data on these same routes.)

### 5.4 Persistence is per-team folders, not tables

There are no a2ax tables and no DDL. A team's a2ax state is created lazily the first time the transport writes to it: the team's `<teamDir>/messages/` files are produced on demand by `appendJsonl`/`writeJson` (each ensures its parent dir). The team folder itself (`<dataDir>/teams/<teamId>/` with its `team.json` marker) is created by the store's `teams.insert()` when the team is created — that folder must exist before any a2ax call for the team, which is why the transport throws if `dirForTeam` cannot find it.

Cleanup is by folder removal, not SQL cascade. `modify_team`'s delete (`packages/backend/src/server/tools/management.ts:131`) calls `teams.delete(teamId)`, which removes the team's entire on-disk sub-tree in one `rmdir` — nested sub-teams, every agent's files, and the team's `messages/` folder (channels, messages, tasks, tokens, cards) all live under it, so they are deleted together with no per-table cascade to maintain (`:126-128` comment). `scripts/seed-demo.ts:21` resets state with `clearStore()` (a store helper that wipes the data dir) instead of deleting individual a2ax tables. Agent IDs stored in messages/tasks/tokens (`fromAgentId`, `requestorId`, `assigneeId`, token `agentId`) are plain strings with no referential constraint — they may hold cofounder/user sentinel UUIDs that have no `agent.json`, exactly as before.

### 5.5 Currently-unused surface (grep-verified, no call sites outside `packages/a2ax`)

- Protocol methods: `createGroup`, `joinGroup`, `leaveGroup`, `completeTask`, `registerCard`, `getCard`, `discoverAgents`, `issueToken`, `authenticate`, `authorize`, `expireMessages`. (`sendToGroup` *is* reachable via the messages POST route, but since `createGroup`/`joinGroup` are never called, no group channels or memberships exist for it to target in practice.) `listMessages`/`listTasks` are now exercised by the dashboard routes (§5.3), so they are no longer dormant.
- Transport methods never reached even indirectly: `listChannels`, `getMembers`, `getMemberships` (only as an internal step of `queryMessages`), `revokeToken`. (`listTasks` and `listTeamMessages` are now reached through the protocol's read views.)
- The `cards.json` and `tokens.json` files are never produced: no host code calls `registerCard`/`issueToken`, so `upsertCard`/`createToken` never run and those files are never written for any team.
- The whole auth layer (scopes, tokens) and agent-card discovery are dormant: agents are trusted implicitly inside the process.
- `expireMessages` is never scheduled, so the `expiresAt` stamped on direct/broadcast/group messages is never enforced in production (task-channel messages carry no expiry at all), and `markExpired`'s `log.jsonl` rewrite never fires.
- The `./transport/memory` subpath export is consumed only by the package's own tests; the production host uses `./adapters/json-file` exclusively.

## 7. Behavior contract pinned by tests (`packages/a2ax/tests/protocol.test.ts`)

All package tests run the `A2AX` class over `MemoryTransport` (the json-file adapter has no package-level test; its production behavior is pinned instead by the backend's `a2ax.test.ts` over the real file store, §5.1). They pin:

- Direct: delivery to the recipient, exclusion of the sender's own messages, and read-once semantics via `markContextRead` (`:17-44`).
- Broadcast: delivery to all other agents; a broadcast read by one agent **stays unread for every other agent** (the per-recipient reads regression test, `:59-73`); the sender never sees their own broadcast.
- Groups: member-only delivery, per-member read isolation, join grants visibility (including history) (`:84-139`).
- Tasks: `createTask` produces a `submitted` task and an urgent `task.create` message to the assignee; the `submitted → accepted → working → completed` lifecycle works through `updateTaskState`/`completeTask`; `submitted → completed` via `updateTaskState` throws `Invalid transition` (`:142-195`).
- Cards: `createAgentCard` defaults (`capabilities.broadcast === true`) and **team-scoped discovery** — `discoverAgents("team-1")` must not return another team's cards (`:197-241`).
- Auth: issued tokens authenticate and pass `message:send` but fail `admin`; unknown tokens return null (`:244-263`).
- Context: empty context formats to `""`; `maxContextMessages` caps the merged result (`:265-285`).

## 8. Edge cases and internal inconsistencies (current behavior)

- `completeTask` does not call `isValidTransition`, so any task — including one already `canceled` or `rejected` — can be force-completed (`packages/a2ax/src/core/protocol.ts:262-288`).
- `MessageStatus` values `delivered` and `read` exist in the type but are never written; read state lives entirely in the `reads.jsonl` log / the in-memory `reads` set.
- `JsonFileTransport.queryMessages` filters for relevance *before* slicing by `limit` (it works over the full in-memory array), so the limit always yields relevant rows. This fixes the old Drizzle adapter's hazard, where `LIMIT` ran in SQL before the JS relevance filter and a busy team could starve an agent's context window with rows that were discarded afterward.
- `JsonFileTransport.addMember` dedups (like the memory transport), so duplicate membership rows are not possible — unlike the old Drizzle adapter, whose `onConflictDoNothing` was inert against a constraint-free table.
- `JsonFileTransport.updateTask` **merges** `metadata` (`{ ...task.metadata, ...input.metadata }`), matching the memory transport — the old Drizzle adapter replaced it, so this cross-transport divergence is gone.
- `getAgentContext` keeps the oldest unread messages when truncating, not the newest.
- `createGroup` attributes its `system.created` message to `memberIds[0]`; an empty member list writes `fromAgentId: undefined`.
- `ensureChannel` is non-atomic (get-then-create), but harmless under the single-process, single-writer JSON-file store: synchronous transport IO cannot interleave with another tick, and a duplicate `createChannel` simply re-writes the same `channels.json` entry (last write wins) rather than raising a constraint error.
- `markExpired` rewrites the whole `log.jsonl` for each affected team; with `expireMessages` never scheduled (§5.5) this code path does not run in production, so message logs only ever grow by append.
- The lazy hydration walk (`discoverTeamMessageDirs`) reads every team's files into memory on the first transport call, so a process with a large data tree pays a one-time startup cost proportional to total message history; thereafter all reads are in-memory.

### Idiomatic-Python choices as they apply here

- **Pydantic v2 replaces the bare TS interfaces, with camelCase preserved.** Every shape in §2 is a `BaseModel` carrying `model_config = ConfigDict(populate_by_name=True)` and **camelCase field names verbatim** (`channelId`, `fromAgentId`, `createdAt`, `expiresAt`, `messageIds`, …), so the JSON the frontend and the read-side dashboards consume is byte-identical to the TS runtime (`a2ax/__init__.py` header: "field names stay camelCase to match the TS JSON exactly"). Union literals (`ChannelType`, `MessageStatus`, `MessageRole`, `GeneralKind`, `TaskKind`, `SystemKind`, `TaskState`, `Scope`) are `typing.Literal` — the Python equivalent of the TS string-literal unions, validated at the model boundary the way Zod would. The one deliberate loosening is `MessageKind = str` (`message.py:29`), left as a plain `str` rather than the literal union "so the union of literals does not over-constrain round-tripping" — kinds like `task.create`/`task.status`/`task.result` flow through unvalidated, matching the TS `MessageKind` union's permissiveness in practice.
- **The `Transport` interface is a `typing.Protocol`, not an ABC.** `transport.py:43` declares `Transport` as a `@runtime_checkable` `Protocol` with all **22** async methods (5 messages + 7 channels + 4 tasks + 3 cards + 3 auth), the structural-typing analogue of the TS `interface`: `MemoryTransport` and `JsonFileTransport` satisfy it by shape, with no `implements`/inheritance. `MessageQuery` is itself a Pydantic model (`transport.py:31`) carrying `{teamId, agentId, unreadOnly?, limit?, channelType?}`.
- **`async` everywhere, even where the work is synchronous.** Every transport method is `async def` to match the TS `Promise`-returning interface (`transport.py` header: "All methods are async … even though MemoryTransport's logic is synchronous in-memory work"). The protocol facade (`protocol.py`) is correspondingly `async`, so call sites `await a2ax.send_direct(...)`, `await a2ax.get_agent_context(...)`, etc.
- **Blocking fs is dispatched off the event loop.** `JsonFileTransport` keeps its 22 methods `async` but pushes the actual disk IO into a worker thread: each public coroutine is a one-line `await anyio.to_thread.run_sync(self._<op>_sync, …)` wrapping a synchronous `_<op>_sync` body (`json_file_transport.py:163-451`). The fs primitives in `file_store.py` (`read_json`/`write_json`/`read_jsonl`/`append_jsonl`/`rewrite_jsonl`/`discover_team_message_dirs`) stay plain blocking helpers, the exact mirror of the TS synchronous `file-store.ts`, and use Python 3.14 PEP-695 generics (`def read_json[T](path, fallback: T) -> T`). This is the same `anyio.to_thread` pattern the store layer uses (ARCHITECTURE.md, "blocking fs via `anyio.to_thread`").
- **The store lock is *not* taken inside a2ax — and that is the deliberate boundary.** The fidelity risk register's item 1 (the `asyncio.Lock` around every store read-modify-write) governs the agent store, *not* the a2ax transport. a2ax is a separate single-writer in-memory structure with its own write-through, so it carries no lock: the comment is explicit that the json-file adapter is "Single-process, single-writer, like the rest of the file store" (`json_file_transport.py:18`). Because `anyio.to_thread.run_sync` dispatches each `_<op>_sync` body as one indivisible unit (no `await` inside it), the get-then-create in `_ensure_channel`/`create_channel` cannot interleave with another tick's mutation — preserving the same `ensureChannel` non-atomicity-is-harmless property the TS chapter notes for the single-writer store (§3, §8). The MIGRATION note that per-team agents run sequentially (deferred divergences) further means no two ticks touch the bus concurrently in the first place.
- **Hydration and write-through are line-for-line the TS model.** `JsonFileTransport.__init__` (`json_file_transport.py:62`) takes `teams_root` and holds the full state in memory — `_messages: list[Message]`, `_reads: set[str]` keyed `${messageId}:${agentId}`, `_channels`/`_tasks`/`_cards`/`_tokens` dicts, `_members: list[ChannelMember]` — exactly mirroring `MemoryTransport`'s structures. `_hydrate()` (`:79`) runs once on the first call, walking the team tree via `file_store.discover_team_message_dirs` and reviving each team's files with `Model.model_validate(raw)` (`_load_dir`, `:87`); `_dir_for_team` (`:110`) re-walks once if a team folder appears after hydration and raises `a2ax: team {team_id} folder not found under {teams_root}` otherwise. Per-collection persistence filters the in-memory collection down to one team before `write_json` (`_persist_channels`/`_persist_members`/`_persist_tasks`/`_persist_cards`/`_persist_tokens`, `:126-159`), while `log.jsonl` and `reads.jsonl` are appended one line at a time — matching the TS adapter's atomic-rewrite-vs-append split.
- **Date revival is selective, exactly as in the TS adapter.** Because the row shapes are Pydantic models with only the declared top-level date fields typed `datetime` (`createdAt`/`expiresAt`/`joinedAt`/`updatedAt`), `model_validate` revives only those; the opaque `payload`/`metadata`/`parts`/`artifacts`/`data` blobs are `dict[str, object]`/`list[...]` and round-trip verbatim, so nested ISO-looking strings inside them stay strings (risk-register item 2). On write, `_dump(model)` calls `model.model_dump(mode="json", by_alias=True)` (`json_file_transport.py:50`) to emit ISO-8601 date strings and camelCase keys — the `JSON.stringify(Date)` equivalent.

### Load-bearing fidelity behaviors preserved

- **Per-recipient read tracking (risk-register item 5).** Reads are a `set[str]` keyed `${messageId}:${agentId}` via the shared helper `_read_key` (`transport.py:87`), in **both** transports — never a global status flag on the message. The unread filter in `_query_messages` excludes a message only for an agent whose `_read_key(m.id, agentId)` is in the set (`transport.py:300`), so a broadcast read by one agent stays unread for every other. `JsonFileTransport.mark_read` (`:219`) appends `{messageId, agentId, readAt}` to the team's `reads.jsonl` and skips keys already in the set (no duplicate append), exactly the TS behavior. The `MessageStatus` literals `delivered`/`read` exist on the model (`message.py:14`) but are never assigned — read state lives entirely in the set/`reads.jsonl`, matching §8.
- **`complete_task` does not validate the transition (risk-register item 6).** `protocol.py:285-319` carries an explicit comment — "completeTask FORCE-sets state=completed from any state (incl. terminal) — it does NOT validate the transition, unlike updateTaskState" — and unconditionally calls `update_task(task_id, UpdateTaskInput(state="completed"))` after only the not-found check, whereas `update_task_state` (`:252`) gates on `is_valid_transition(task.state, new_state)` and raises `Invalid transition: {from} -> {to}`. The `submitted → completed` divergence between the two paths is thus preserved verbatim.
- **`direct_channel_id` sorts the pair and `query_messages` reconstructs it for relevance (risk-register item 7).** `direct_channel_id(a, b)` returns `direct:{min}:{max}` over the sorted pair (`channel.py:38`), so the channel is identical regardless of sender. The relevance test `_is_relevant` (`transport.py:316`) rebuilds the expected id with `m.channelId == direct_channel_id(agent_id, m.fromAgentId)` for `direct`, treats every `broadcast` as relevant, gates `group` on membership and `task` on requestor/assignee involvement, and — first of all — returns `False` when `m.fromAgentId == agent_id` so an agent never sees its own messages. This is the single shared `_query_messages` pipeline (`transport.py:279`) used by *both* transports, so `MemoryTransport` and `JsonFileTransport` cannot drift.
- **Relevance is filtered before the `limit` slice.** `_query_messages` applies team → unread → channelType → relevance, *then* sorts ascending by `createdAt`, *then* head-slices by `limit` (`transport.py:294-313`), over the full in-memory list. The limit always yields relevant rows — the same fix the TS json-file adapter made over the old Drizzle `LIMIT`-in-SQL hazard (§8). There is no SQL layer here at all.
- **`get_agent_context` four-query assembler, oldest-kept truncation.** `protocol.py:323` issues four separate `query_messages` calls (one per `direct`/`broadcast`/`group`/`task`, each `unreadOnly=True`, `limit=max_context_messages`), concatenates, `sorted(... key=lambda m: m.createdAt)`, and slices `[: self._max_context_messages]` — ascending sort + head slice, so truncation keeps the **oldest** unread and drops the newest (§3, §8). `_format_context` returns `""` for an empty list and otherwise emits the identical `--- Messages since last tick ---` block with the same per-channel prefixes (`_format_prefix`, `:450`: `[direct from X]:`, `[broadcast from X]:`, `[<channelId> from X]:` for groups, `[<channelId> from X] (<kind>):` for tasks).
- **Team-scoped card discovery and the metadata-smuggled `teamId`.** `AgentCard` has no `teamId` field; the owning team rides on `metadata.teamId` (`types.py:83`), read by the shared `_card_team_id` helper (`transport.py:92`). `list_cards` filters strictly on `_card_team_id(c) == team_id` in both transports (`transport.py:262`, `json_file_transport.py:420`), so a team never sees another team's cards. `create_agent_card` fills the same defaults (`streaming/pushNotifications/extendedAgentCard=False`, `broadcast/groups/tasks=True`, `skills=[]`). `generate_token` returns 32 random bytes as lowercase hex via `secrets.token_hex(32)` (`token.py:61`) — the `crypto.getRandomValues` equivalent — and `DEFAULT_SCOPES` is the same 8-scope subset; `has_scope` returns true for the scope **or** `admin`.

### Host wiring (write path, read path)

The exercised protocol surface is identical to the TS host (§5.2: `send_direct`, `broadcast`, `send_to_group`, `create_task`, `update_task_state`, `get_agent_context`, `mark_context_read`):

- **Singleton.** `a2ax_singleton.get_a2ax()` lazily builds one `A2AX` over `JsonFileTransport(teams_root())` with `max_context_messages=20` and 7-day expiry, then memoizes it; `reset_a2ax_for_tests()` drops the cache so tests that repoint `SH_DATA_DIR` get a fresh transport (`a2ax_singleton.py:26-43`) — the exact `getA2AX`/`resetA2AXForTests` contract, including the "transport captures the teams root at construction" caveat.
- **Tick write path.** `tick.py` calls `args.a2ax.get_agent_context(team.id, agent.id)` (`:458`), injects `ctx.formatted` into the run config as `a2axContext` (`:491`, passed through only when truthy), and after a successful run calls `args.a2ax.mark_context_read(agent.id, ctx.messageIds)` (`:512`). The runner appends that context to the tick prompt at `meta_agent/runner.py:297-298` (`if config.a2axContext: prompt += f"\n\n{config.a2axContext}"`). On failure, `_fail_agent` (`:819`) double-writes to `app_events` **and** fire-and-forgets `_safe_broadcast` → `a2ax.broadcast(...)` (`:847-868`) so peers see the failure next tick.
- **Agent tools.** The built-in `send_message` and `broadcast` tools call `ctx.a2ax.send_direct` / `ctx.a2ax.broadcast` (`tools/default_tools.py:57,71`). As in TS, the meta-agent library depends only on a structural seam: `A2AXSender` is a `typing.Protocol` of just `{send_direct, broadcast}` (`tools/types.py:53`), so the library carries no concrete a2ax import; the tick handler supplies the real instance.
- **Messages API.** `POST /api/team/{id}/messages` translates the cofounder/user POV sentinels to their agent UUIDs (`routes/team.py:565-577`), then dispatches on `channelType` to `broadcast`/`send_to_group` (requires `channelId`)/`send_direct` (default, requires `toAgentId`), returning 201 with `model_dump(by_alias=True, exclude_none=True)` so unset optionals are omitted (not `null`) to match `JSON.stringify`. `GET` calls `get_agent_context` without marking read.
- **Read path (dashboards).** The three dashboard routes read through the protocol, not a query layer: `a2ax.list_messages(team_id, 200)` for the agent hub, `a2ax.list_messages(team_id, 1000)` + `a2ax.list_tasks(team_id)` for conversations, and `a2ax.list_tasks(team_id, …)` for tasks (`routes/team.py:171,409,426,649`) — delegating to `list_team_messages`/`list_tasks`, which are unfiltered chronological reads (no relevance, no read filter), exactly the §5.3 contract.
- **Persistence is per-team folders, deleted by sub-tree removal.** `modify_team`'s delete calls `await teams.delete(team_id)`, which removes the team's entire on-disk sub-tree including its `messages/` folder in one operation (`tools/management.py:149-161`), with no per-table cascade — the §5.4 model.

### Deferred / known divergences relevant to this chapter

- **Module layout is flattened.** The TS `src/{types,core,transport,adapters,storage}/` split becomes flat modules under `a2ax/`; `MemoryTransport` and the `Transport` Protocol share one file (`transport.py`) rather than `core/transport.ts` + `transport/memory.ts`. The `a2ax_singleton.py` host glue lives at the package root (it needs the host store's `teams_root()`), not inside `a2ax/`. No behavior changes — purely structural.
- **The dormant surface is dormant here too.** As in TS (§5.5), `create_group`/`join_group`/`leave_group`/`complete_task`/`register_card`/`get_card`/`discover_agents`/`issue_token`/`authenticate`/`authorize`/`expire_messages` and the whole auth/agent-card layer are implemented and tested but unused by the host, so `cards.json`/`tokens.json` are never produced and `expire_messages` is never scheduled (the `expiresAt` stamps are never enforced; `mark_expired`'s `log.jsonl` rewrite never fires in production).
- **Per-team agents run sequentially** in `tick.py` (a deferred MIGRATION divergence vs the TS `Promise.allSettled` per pass). For this chapter that is reinforcing rather than risky: it guarantees no two ticks mutate the lock-free a2ax bus concurrently, so the single-writer assumption that makes `_ensure_channel`'s get-then-create safe always holds.
