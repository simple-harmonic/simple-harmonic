Simple Harmonic — v0.0 design mockup

generated 2026-05-18 · /plan-design-review · dark/amber, bidirectional chat onboarding

Brand architecture: Simple Harmonic is the v0.0 product (the meta-agent platform). Simple Harmonic is the parent company. Future products (Spring for cross-device comms, Resonance/Circuit for the marketplace) inherit the simple-harmonic-motion theme.

Direction locked: dark theme, amber accent. Onboarding flow upgraded from single-textarea-paste to bidirectional chat with the meta-agent: brainstorming, follow-ups, pushback. The chat IS the product's first impression. The textarea version is dead.

What you're reviewing: three states of the chat onboarding (initial, mid-brainstorm, approval moment), then the active team view, paused state, and error state. All dark/amber.

1. Onboarding chat — initial state

First visit. No vision yet. The meta-agent greets and frames what comes next. Goal: feel like talking to a real ops person, not filling out an intake form.

Design intent. No big headline shouting "Welcome." Meta-agent introduces itself in the first message, in voice. The input field is anchored at the bottom (chat convention, expected affordance). Top bar has minimal product chrome plus a "new chat" affordance for power users. The chat surface is generous on width so messages breathe; not the 480px Intercom-style narrow column.

2. Onboarding chat — mid-brainstorm (with pushback)

User has answered the first prompt. Meta-agent asks a clarifying follow-up. User suggests something ambitious. Meta-agent pushes back with reasoning, not just agreement.

Design intent. User messages right-aligned, meta-agent messages left-aligned with the M-badge. Pushback is explicit: meta-agent disagrees in clear voice, with reasoning. This is the "AI cofounder" brand promise made visible — it's not a yes-machine. The thinking-indicator (small pulsing dot) signals when meta-agent is composing. Token-by-token streaming would make the demo feel alive.

Six is more than you'll supervise effectively. Solo founders running 6+ agents typically burn out on review fatigue in the first two weeks — too many narration entries to scan, too many "approve this draft" decisions. The whole point of me is to reduce your decision load, not multiply it.

My counter-proposal: start with 3 agents that cover your biggest pain, plus a 4th if you really want refund-flow visibility. Add more as you see which ones earn their keep.

  • content-drafter — writes X posts from your customer questions, you approve before posting

  • refund-flow (optional 4th) — surfaces refund requests with one-click approve/deny

I'd drop analytics, blog, and email for now — analytics doesn't need its own agent (we can add it to research-summarizer), and blog/email need bigger weekly time blocks that solo agents struggle with. Add later if it matters.

3. Onboarding chat — approval moment (spawn)

User and meta-agent have aligned. Final agent list is on the table. User reviews, optionally tweaks names/schedules, hits Spawn. Team boots in real-time after this.

Design intent. The approval moment is a real UI step, not a buried button in the chat. A summary card pins the proposed team at the bottom of the conversation with inline edit affordances. Spawn is the one big accented button. Below it, a small "keep discussing" link returns to chat. The user always has one keystroke between "I changed my mind" and "spawned a team I didn't want."

Team is spawned and running. The demo's headline. Meta-agent supervises, narration runs live, Pause Team is prominent because override is the brand.

Design intent. Split 2/3 graph + 1/3 narration. Meta-agent visually elevated above worker agents to communicate hierarchy. Inline edit + disable icons on every agent (override at every layer). 5. Paused state

Pause Team was clicked. All agents halt, meta-agent stops approving ticks. Paused-ness must be obvious within the first second of looking.

Design intent. Amber strip at top declares team pause without dimming the whole UI. Status pills shift to muted gray. Button flips to "Resume." Narration shows clean last-line entries, no live indicator.

6. Error state (LLM failure during chat)

With bidirectional chat, the "planner fallback to default team" failure mode is much rarer because the meta-agent has multiple turns to clarify. The remaining error to design for: an LLM call fails mid-chat (network, API, rate limit). The chat must degrade gracefully without losing the conversation history.

Design intent. Error appears as an inline system message in the chat, not a modal or full-page error. The user's last message is preserved (not wiped). A retry button sits where the meta-agent reply would have appeared. Tone: factual, no apology-spam. The conversation can resume from any point.

Notes

Six surfaces, dark/amber direction throughout. Chat onboarding replaces single-textarea hero. Empty state dissolves because chat IS the empty state. Error state redesigned around the chat surface.

Scope addition from this change:

  • Chat UI surface (~1-2 build days): message list, streaming assistant replies, input handling, scroll/focus behavior, message persistence in DB.
  • Eng-review D5 (planner contract) revised: planner is now a multi-turn chat ending in a `spawn_team` tool-use call when both parties agree. Retry logic still applies to the final spawn step.
  • New DB tables: `chat_messages` and `chat_sessions`, scoped to team.
  • LLM cost per onboarding goes up slightly (multi-turn vs single-shot), but onboarding is once-per-user so the cumulative effect is small.
