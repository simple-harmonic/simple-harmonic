# 07 — Frontend (UI)

The Simple Harmonic UI is split across two locations: a workspace package, `packages/frontend`, that holds all reusable React components, hooks, and helpers (chat, team views, sidebar, theming, narration, trace), and the Next.js App Router tree in `src/app/` that composes those components into pages. Every page except `src/app/(app)/f/[id]/page.tsx` is a client component; there is no server-side data fetching — all data comes from client `fetch` calls against the app's own `/api/*` routes, driven by mount-time loads, fixed-interval polling (2s–30s depending on surface), and three SSE-over-fetch streams: meta-agent chat, team narration, and the play-by-play trace stream `GET /api/team/[id]/trace` consumed by the PR #12 trace UI (see [TraceView](#traceview)). Styling is Tailwind CSS v4 with a Carbon-flavored custom token set defined in `src/app/globals.css`, light/dark theming via a `.dark` class managed by a custom `ThemeProvider`, and a single shadcn/Base UI button primitive that is currently unused by any page.

## Workspace wiring

- `packages/frontend/package.json` declares `@simple-harmonic/frontend` v0.1.0 with `"exports": { "./*": "./src/*" }` — consumers import source files directly (e.g. `@simple-harmonic/frontend/components/sidebar`). The package carries **only dev dependencies** (vitest, jsdom, `@vitejs/plugin-react`); React, `clsx`, `tailwind-merge`, `class-variance-authority`, and `@base-ui/react` are hoisted from the root `package.json` (`package.json:29-50`).
- The root `tsconfig.json` maps `@simple-harmonic/frontend/*` → `./packages/frontend/src/*` and `@simple-harmonic/backend/*` → `./packages/backend/src/*` (`tsconfig.json:21-25`), so Next bundles the workspace sources as in-repo files; `next.config.ts` has no `transpilePackages` and only sets `devIndicators: false`.
- Frontend components import **backend identity constants directly**: `USER_AGENT_ID`, `COFOUNDER_AGENT_ID`, `DEFAULT_COFOUNDER_NAME`, `getTeamHumans`, `resolveCofounderName` from `@simple-harmonic/backend/lib/meta-agent/identity` (`packages/frontend/src/components/team/agent-messages-view.tsx:4-9`, `agent-pov-view.tsx:4`, `chat/approval-card.tsx:5`) and the `SpawnTeamAgent` type from `@simple-harmonic/backend/lib/meta-agent` (`chat/use-chat.ts:4`).
- Tests run under vitest + jsdom with aliases `@/` → `packages/frontend/src` (`packages/frontend/vitest.config.ts`). Two suites exist: `tests/unit/narration.test.ts` and `tests/unit/utils.test.ts`.
- `components.json` is the shadcn config: style `base-nova`, RSC on, Tailwind CSS at `src/app/globals.css`, base color neutral, CSS variables on, icon library lucide, aliases `@/components`, `@/lib/utils`, etc. Note those aliases resolve into the Next app's `src/`, while the only generated primitive (`button.tsx`) actually lives in `packages/frontend/src/components/ui/`.

## Layout, theming, fonts

`src/app/layout.tsx` (server component) loads **Inter** (`--font-sans`) and **IBM Plex Mono** (`--font-mono`) via `next/font/google`, sets metadata (`title: "Simple Harmonic"`, description "Your company, built by agents, run by agents, managed by agents (with you)"), and injects `THEME_INIT_SCRIPT` via `dangerouslySetInnerHTML` in `<head>` so the `.dark` class is applied before first paint (`src/app/layout.tsx:41-45`); `<html>` uses `suppressHydrationWarning` because the script intentionally diverges from SSR markup. The body wraps everything in `ThemeProvider` and mounts `MobileNotice`.

`ThemeProvider` (`packages/frontend/src/components/theme-provider.tsx`) stores `"system" | "light" | "dark"` under `localStorage["simple-harmonic-theme"]`, resolves "system" from `prefers-color-scheme` and live-tracks OS changes, and toggles `.dark` on `<html>`. `useTheme()` returns a no-op default instead of throwing when used outside the provider (`theme-provider.tsx:101-109`). The settings page's theme picker calls `setPref` directly.

`MobileNotice` (`packages/frontend/src/components/mobile-notice.tsx`) is a dismissable full-screen overlay shown at viewports ≤767px ("Best on desktop … Mobile support comes in v0.3").

`src/app/globals.css` imports `tailwindcss`, `tw-animate-css`, and `shadcn/tailwind.css`, defines `@custom-variant dark`, and declares an `@theme inline` block exposing both the standard shadcn tokens (`--color-background`, `--color-primary`, chart and sidebar colors, radius scale) and Simple Harmonic's own tokens: `fg/fg-muted/fg-faint`, `bg/bg-elev/bg-input`, `border/border-strong`, `brand/brand-soft` (IBM blue `#0f62fe`), status colors `running` (green) / `paused` (gray) / `error` (red), and identity colors `user/user-soft` (blue) and `meta/meta-soft` (orange `#ff832b`) (`src/app/globals.css:50-67`). `:root` is the Carbon-Light palette; `.dark` swaps to Carbon dark (`globals.css:81-190`). Note the `@theme` font tokens are the literal stacks `"Inter", system-ui` / `"IBM Plex Mono", ui-monospace` rather than references to the `next/font` CSS variables of the same names.

The only shadcn/Base UI primitive is `packages/frontend/src/components/ui/button.tsx`: `@base-ui/react/button` wrapped in `cva` variants (default/outline/secondary/ghost/destructive/link; sizes xs→lg plus icon sizes). Nothing in `src/` or the rest of `packages/frontend` imports it — all pages style raw `<button>` elements with token utility classes. `packages/frontend/src/lib/utils.ts` exports the standard `cn = twMerge(clsx(...))` helper (used only by `button.tsx`); its tests pin merging, conditional classes, and Tailwind dedup (`p-4` + `p-2` → `p-2`).

## Sidebar

`packages/frontend/src/components/sidebar.tsx` is a client component (wrapped in `Suspense` because it uses `useSearchParams`). Behavior:

- Fetches `GET /api/teams` once on mount, then eagerly fetches `GET /api/team/[id]` for **every** team to fill `teamAgents` and `teamCofounderNames` maps so any tree node can expand without a fetch (commented as fine at "<20 teams" scale, `sidebar.tsx:74-92`). No polling — sidebar data is mount-time only.
- Builds a nested team tree from `parentTeamId` (`buildTeamTree`, `sidebar.tsx:244-261`) and renders it with `TeamTreeNode`: chevron toggles, auto-expansion of the active path (derived from the `/f/[id]` pathname and `?agent=` search param), run-state indicators (dot for root teams, group icon tinted `--color-running`/`--color-paused` for sub-teams).
- Inside an expanded **root** team it pins two human/AI entries before the agent list: "You" (links to `?agent=user`, blue person icon) and the cofounder (links to `?agent=meta`, orange sparkle icon, name from the team's `cofounderName` or the literal fallback "Harmon") — deliberately not repeated on sub-teams (`sidebar.tsx:356-385`). Agents follow with status dots (`running`/`errored`/`awaiting_approval`/`paused` → green/red/brand/gray).
- Header: "Simple Harmonic" wordmark linking to `/`, a collapse toggle (collapses to a 48px rail with a single expand button), and a "+" button linking to `/new`.
- Footer: a user chip (initial avatar, display name, role read from `localStorage["sh:user-profile"]` and kept fresh via `storage` events) opening a popover menu with Profile, Settings, and "Log out" — the last simply sets `window.location.href = "/login"` without calling any API (`sidebar.tsx:194-208`).

## Chat UI (`/new`)

### Message rendering (`packages/frontend/src/components/chat/message.tsx`)

`ChatMessageData` has roles `user | assistant | error`, optional `isPushback` and `timestamp`. Four renderers:

- `AssistantMessage` — orange "M" badge, label "meta-agent", HH:MM:SS timestamp, optional "· pushback" marker, body run through `FormattedText` (the only markdown supported is `**bold**` via regex split, `message.tsx:3-16`), plus a pulsing block cursor while streaming.
- `UserMessage` — a right-aligned bubble — `flex justify-end`, `max-w-[60ch]`, `bg-bg-input` — with no badge, label, or timestamp (`packages/frontend/src/components/chat/message.tsx:81-89`).
- `ErrorMessage` — "!" badge labeled "connection error", with an optional Retry button.
- `ThinkingIndicator` — meta-agent badge with three pulsing dots, shown while the streaming placeholder is still empty.

### `useChat` state machine (`packages/frontend/src/components/chat/use-chat.ts`)

State: `messages` (seeded with a hard-coded greeting from "Harmon" asking what the company does, who pays, and what's eating the week, `use-chat.ts:33-39`), `status: "idle" | "streaming" | "error"`, `spawnProposal`, `credentialRequest`.

`sendMessage(text)`:
1. No-op while `status === "streaming"`.
2. Optimistically appends the user message and an **empty assistant placeholder** (id tracked in `streamingIdRef`), sets `status = "streaming"`, clears any prior spawn proposal.
3. POSTs the full user/assistant history (error messages filtered out) to `POST /api/chat` and reads the response body as a stream, splitting on `\n\n` and parsing `data: ` lines (SSE-over-fetch).
4. Event kinds: `token` appends text to the placeholder; `spawn` replaces content and sets `spawnProposal` ({teamName, cofounderName, agents} — the event's `parentTeam` field is **dropped**, see the spawn-handoff note below) + `status = "idle"`; `request_credential` sets `credentialRequest` ({key, label, reason, helpUrl}) + idle; `done` → idle; `error` removes the placeholder, appends an `error` message, `status = "error"`. Network failure does the same.
5. **Unhandled event — `modify_agent`:** the chat handler emits a sixth event type, `modify_agent` (`packages/backend/src/server/api/chat.ts:77-90`; the Next route `src/app/api/chat/route.ts` is a thin re-export), after applying the planner's agent edit to the store server-side via `applyModifyAgent`. `useChat` has no branch for it, so the event — including its confirmation `content` and `applied: {ok, error?}` outcome — is silently discarded. The modification happens, but the UI shows only whatever tokens streamed before the tool call; when the model emitted no text, the placeholder stays empty and, once the stream ends and status flips to idle, renders as an *empty* `AssistantMessage` (the page's empty-message skip applies only while streaming, `src/app/(app)/new/page.tsx:102`). The `done` event's `content` field is likewise ignored — harmless when tokens streamed (it duplicates them), but the planner's no-text fallback `"I need a moment. Try again."` (`planner.ts:466`) is never displayed.
6. `retry()` strips error messages and re-sends the last user message. `clearSpawnProposal` / `clearCredentialRequest` reset the side-channel state.

### Page composition (`src/app/(app)/new/page.tsx`)

Header shows a status string ("no agents yet" → "thinking..." → "N messages" → "aligned, ready to spawn"). The scroll container auto-scrolls on message/proposal/credential count change. Empty streaming placeholders are skipped and replaced by `ThinkingIndicator`. Below the transcript:

- `ApprovalCard` (`packages/frontend/src/components/chat/approval-card.tsx`) renders the proposed team with **inline-editable** team name, cofounder name (placeholder = `DEFAULT_COFOUNDER_NAME`), and per-agent name/role rows plus a read-only schedule chip (`formatSchedule` → "every Ns/m/h"). "Spawn N agents →" calls back with the edited payload; "keep discussing" dismisses. Agent rows are keyed by `agent.name` even though the name is editable.
- On spawn the page POSTs `/api/spawn` and, on success, routes to `/f/{teamId}`; meanwhile a `SpawningScreen` ("Spinning up N agents...") replaces the chat. **Spawn-handoff gap:** the POST body is exactly `{agents, teamName, cofounderName}` (`src/app/(app)/new/page.tsx:54-65`), while the handler also accepts `parentTeam`, `parentTeamId`, `goal`, and `noHarmon` (`packages/backend/src/server/api/spawn.ts:47-51`). The planner's `spawn` SSE event carries `parentTeam` for sub-team proposals, but `useChat` drops it and the card never forwards it — so a proposed *sub*-team is always created as a **root** team, and (being root, without `noHarmon`) gets an auto-spawned Harmon cofounder agent it was never proposed to have (`spawn.ts:106-117`). The route's `{teamId, parentTeamId}` response is read only for `teamId`.
- `CredentialRequestCard` (`packages/frontend/src/components/chat/credential-request-card.tsx`) shows label/reason/help link with a password input; submit POSTs `{key, value}` to `/api/settings/credentials` and flips to a green "configured" state. Copy states the value is "Encrypted and stored in Apollo, Simple Harmonic's secrets manager" and never stored where agents can read it.
- `ChatInputBar` (`packages/frontend/src/components/chat/input-bar.tsx`) is an uncontrolled textarea (ref-based), Enter to send / Shift+Enter for newline, disabled while streaming; placeholder switches to "Push back or tweak the proposal..." when a proposal is showing.

## Team view (`/f/[id]`)

`src/app/(app)/f/[id]/team-view.tsx` is the client shell. POV is the `?agent=` search param (default `"team"`):

- `team` → `ApprovalQueue` + `TeamDashboard`.
- `meta` / `user` → `AgentMessagesView` with `initialPovId` `"cofounder"` / `"user"`.
- any other value → looked up in `agents`; match renders `AgentPovView`, otherwise "Agent not found".

The header offers click-to-rename (PATCH `/api/team/[id]` with the new `name` plus the existing `metaAgentPrompt`/`cofounderName`, `team-view.tsx:110-118`), a paused/running indicator with tick count, token/cost estimates, and a Pause/Resume button calling `togglePause`. In-page POV switches use `window.history.pushState` + a synthetic `PopStateEvent` rather than router navigation (`team-view.tsx:187-190, 229-232`).

### `useTeam` hook (`packages/frontend/src/components/team/use-team.ts`)

Four concurrent data channels:

1. **Initial load** — `GET /api/team/[id]` once: `team` (id, name, paused, tickCount, metaAgentPrompt, cofounderName), `agents`, `childTeams`, `childAgents`.
2. **10s poll** while the team is unpaused — re-fetches the same endpoint; the comment claims the poll doubles as the dev-mode tick driver ("In production, Vercel cron hits /api/tick independently", `use-team.ts:75-76`) — that claim is stale: the `GET /api/team/[id]` handler never fires a tick; dev ticking actually comes from the 10s self-POST loop in `src/instrumentation.ts` (or, on the standalone backend host, its in-process tick loop). Each poll also synthesizes ephemeral narration entries (`actionType: "thinking"`, description "processing...") for agents currently `inFlight`.
3. **Heartbeat** — `POST /api/team/[id]/heartbeat` immediately and every 30s to keep the team alive while the page is open.
4. **Narration SSE** — once the team has loaded, a long-lived `GET /api/team/[id]/narration` fetch is parsed as SSE. `history` events replace the feed; `update` events prepend deduplicated entries. Each raw entry `{id, agentId, actionType, payload, executedAt}` is mapped to a `NarrationEntry` with `agentName` resolved from the agents ref (fallback `"agent"`), `isMeta = actionType.startsWith("meta_")`, `description = describeAction(...)`, and `detail = extractDetail(payload)`. The feed is capped at 100 entries.

`togglePause` POSTs `/api/team/[id]/pause` and prepends a client-side narration entry (`team_paused` / `team_resumed`). `updateAgent`/`updateTeam` merge optimistic patches into local state.

### `TeamDashboard` (`packages/frontend/src/components/team/team-dashboard.tsx`)

Pure presentational in itself — it issues no fetches of its own (though the play-by-play feed mode mounts `TraceView`, which opens its own SSE). Five stat cards — Agents (with running count), Ticks, Tokens In/Out, Est. Cost — all token/cost numbers are **estimates derived from tick count**: `tokensUp = ticks*400`, `tokensDown = ticks*1200`, `cost = (up*3 + down*15)/1e6` i.e. $3/M input + $15/M output (`team-dashboard.tsx:84-86`). Left column: clickable agent cards (status dot, pulsing when `inFlight`, role, "every Ns/m/h" schedule, "thinking..."/status label), then sub-team sections — each child team header links to `/f/{childId}` and its agents are listed indented; clicking a child agent navigates with a full `window.location.href` assignment (unlike direct agents, which use the pushState callback) (`team-dashboard.tsx:144`). A summary row surfaces "N errored" / "N awaiting approval" chips.

Right column (`data-testid="narration-feed"`): the Activity feed. The feed header carries a `feedMode` toggle (added by PR #12) — `useState<"summary" | "steps">("summary")` at `team-dashboard.tsx:77`, rendered as a two-button pill labeled "summary" / "play-by-play" next to the pulsing "live" badge (`team-dashboard.tsx:183-196`). `steps` replaces the feed body with `<TraceView teamId={teamId} agentNames={agentNames} compact />` (`team-dashboard.tsx:207-208`), where `agentNames` maps every direct *and* child agent id to its name (`team-dashboard.tsx:79-80`) so team-wide trace threads are labeled. Summary mode shows the first 30 narration entries (time, agent name, truncated description) with empty-state copy that differs for paused vs waiting.

### `ApprovalQueue` (`packages/frontend/src/components/team/approval-queue.tsx`)

Self-contained banner above the dashboard listing destructive tool calls parked for human sign-off. Polls `GET /api/team/[id]/approvals` every 4s (default `pollMs`, documented against the 10s dev tick loop). Each card names the agent (via the `agentNames` map), shows the tool name and pretty-printed JSON arguments, and offers Approve/Reject buttons that POST `{approvalId, decision}` back to the same endpoint with optimistic removal and reload-on-failure reconciliation. Renders `null` when empty.

### `TraceView`

Added by PR #12. `packages/frontend/src/components/team/trace-view.tsx` is the React component; `packages/frontend/src/lib/trace.ts` is pure data shaping (no React). It renders every agent step — LLM rounds, tool calls, approval pauses, human decisions, tick boundaries — as live-updating per-tick threads, and mounts in two places: the agent-POV `trace` tab (`<TraceView teamId agentId={agent.id} />`, single agent) and the team dashboard's play-by-play feed mode (`<TraceView teamId agentNames compact />`, whole team — omitting `agentId` streams all agents and `agentNames` labels each thread).

**Data channel** — on mount it fetches `GET /api/team/[id]/trace[?agentId=]` and parses the body as SSE with a manual `ReadableStream` reader, splitting on `\n\n` and parsing `data: ` lines (`trace-view.tsx:62-111`); the stream is torn down and reopened when `teamId`/`agentId` change. The server (handler `packages/backend/src/server/api/team/id/trace.ts`; the Next route `src/app/api/team/[id]/trace/route.ts` is a 2-line re-export) emits one `{type:"history", entries}` event on connect — newest 200 entries from `traceEvents.query` (reading the per-agent `trace.jsonl` files via the JSON file store) reversed to chronological — then re-queries every 2s and emits `{type:"update", entries}` with only-new entries (`since: lastSeen` plus a FIFO id-dedupe set capped at 1000; a read error closes the stream). The route also accepts a `?tickId=` filter the UI never sends. Client-side, `history` replaces state, `update` appends id-deduped entries, and state is capped at the newest `MAX_EVENTS = 2000` (`trace-view.tsx:12`); the view auto-scrolls on growth (not on initial render).

**Event rendering** — `buildTickThreads` (`packages/frontend/src/lib/trace.ts:99`) sorts events by `emittedAt` then `seq` (`sortTraceEvents`, `trace.ts:88` — `seq` restarts after a resume, so the timestamp leads) and groups them per `tickId` into `TickThread {tickId, agentId, startedAt, status, outcome, steps}`. `buildThread` pairs `llm_request`→`llm_response` and `tool_started`→`tool_finished` into single `TraceStepRow`s; an unpaired "started" row renders as live/pulsing. Glyph vocabulary: `▶` tick start, `↻` resume after approval, `✻` LLM round, `⏺` tool call, `⊗` tool/tick failure, `⏸` approval pause, `✓`/`✗` human decision, `■` tick finished, `•` unknown event type. Thread status derives from the *last* event: `tick_finished` → `finished`, `tick_failed` → `failed`, `approval_requested` → `awaiting_approval` (outcome "waiting for your decision"), anything else → `live`. Each thread is a bordered block with a header (start time, agent name in team-wide mode, status badge — "live" pulsing green, "done", "failed", "needs approval"; `trace-view.tsx:24-29`); step rows are 12px mono lines with glyph, timestamp (hidden in `compact`), label, duration, and a click/Enter/Space-expandable `<pre>` detail holding pretty-printed tool args/results or full thoughts (`StepRow`, `trace-view.tsx:211-262`). Empty state shows "Connecting…" then "No trace yet · Every step appears here live on the next tick."

Per-agent screen with a status header (name, role, schedule, "thinking..."/status) and five tabs — `dashboard`, `history`, `trace`, `messages`, `config` (`ActiveTab` union, `agent-pov-view.tsx:76`) — plus a `normal | thinking | verbose` view-mode toggle visible only on History.

- **Dashboard tab** — polls `GET /api/team/[id]/agent-hub?agentId=` every 5s. Computes stats from the returned timeline: total actions, active rate (non-noop %), messages sent (counting `message_sent`/`broadcast_sent` plus the same types nested in `multi_action` payloads), messages received, and the same per-action token/cost estimate (actions×400 in / ×1200 out). Shows tool chips and the last five timeline entries.
- **History tab** — same endpoint/5s poll, rendered as a vertical timeline with auto-scroll on growth. `filterTimeline` hides `received` entries and `agent_thought` actions in normal mode (`agent-pov-view.tsx:452-463`). Normal mode is one-line-per-action with compact labels (`describeActionNormal`: `→ peer`, `→→ N peers`, "2 msgs, 1 other", "idle"). Thinking/verbose use cards: action-type chip, fuller `describeAction` text, expandable `multi_action` sub-actions with glyphs (`→`, `→→`, `·`, `○`, `•` from `describeSubAction`); verbose auto-expands everything and appends raw payload JSON in `<pre>` blocks. Received messages render as muted left-arrow cards (content truncated at 200 chars except in verbose).
- **Trace tab** — renders `<TraceView teamId={teamId} agentId={agent.id} />` (`agent-pov-view.tsx:261`), the live play-by-play stream filtered to this agent (see [TraceView](#traceview)). Unlike Dashboard/History this tab does not poll `agent-hub`; it holds its own trace SSE for the time it is open.
- **Messages tab** — delegates to `AgentMessagesView` with `initialPovId` set to this agent. (A complete `MessagesTab` component with its own `/api/team/[id]/messages` 5s poll and a compose box that sends as `USER_AGENT_ID` still exists in the file at `agent-pov-view.tsx:714-860` but is never rendered — dead code.)

### `AgentMessagesView` (`packages/frontend/src/components/team/agent-messages-view.tsx`)

A Slack-like two-pane view of A2AX traffic from a chosen point of view. POV ids are real agent UUIDs or the sentinels `team` (read-only overview of every message), `cofounder`, and `user`; sentinels map to `COFOUNDER_AGENT_ID` / `USER_AGENT_ID` for channel-id computation (`agent-messages-view.tsx:333-339`). Polls `GET /api/team/[id]/conversations?agentId=` and `GET /api/team/[id]/tasks?agentId=` together every 5s.

- **Left pane** has Messages/Tasks tabs. Threads carry channel types `direct | broadcast | group | task`, each with an icon; rows show last-message preview, relative time, and an unread badge counting non-self `pending` messages. The active-tasks badge counts states `submitted/accepted/working/input_required`.
- **Composing is restricted to the human user POV** (`canCompose = povId === "user"`, `agent-messages-view.tsx:429`). The user can start new DMs with any peer not already in a thread (placeholder threads created client-side with channel id `direct:<sortedIdA>:<sortedIdB>`) or a team broadcast (`broadcast:<teamId>`); placeholders with no messages survive poll merges. Sends POST `/api/team/[id]/messages` with `{fromAgentId, content, channelType, toAgentId?|channelId?}`. The direct placeholder id matches the backend's `directChannelId` scheme exactly (`direct:<sorted>:<sorted>`, `packages/a2ax/src/types/channel.ts:29-32`), so it merges cleanly once messages exist. The broadcast placeholder id does **not**: the backend's `broadcastChannelId` is `team:<teamId>` (`channel.ts:35-37`), so after the first broadcast send the server thread comes back under a different `channelId` — "Team Broadcast" appears twice in the list and the still-selected placeholder never shows the message that was just sent.
- **Human-in-the-loop controls**: on a direct thread with a real agent (user POV only), Wake (`PATCH /api/agent/[id]` `{wake: true}`) and Pause/Resume (`{status}`) buttons appear, disabled while the agent is `awaiting_approval`; a 3s flash banner confirms the action (`agent-messages-view.tsx:298-331`). The handler returns **409** for wake/status changes on an `awaiting_approval` agent (`packages/backend/src/server/api/agent/id.ts:47-51`); the client handlers check only `res.ok`, so when the client's 10s-polled status is stale a 409 fails silently — no flash, no error.
- **Message bubbles**: chat-style with self on the right (brand blue), others on the left, name labels on sender change, centered timestamps when >5 minutes elapse, an `urgent` ring, and non-`text` kinds annotated under the bubble. Team-overview mode renders everything left-aligned with sender names in brand color.
- **Tasks tab** shows state badges for the eight A2AX task states (`submitted/accepted/working/input_required/completed/failed/canceled/rejected`, `agent-messages-view.tsx:144-153`) and a detail pane with requestor/assignee/created/updated/description.

A `const humans = getTeamHumans(teamId)` at `agent-messages-view.tsx:191` is computed but never used.

## Cross-cutting facts

**Polling/streaming cadences** — 2s: codex-login auth poll (bounded at 180s); 4s: approval queue; 5s: agent-hub (dashboard + history tabs), conversations + tasks; 10s: team poll (only while unpaused); 30s: heartbeat; SSE streams: `/api/chat` (per send), `/api/team/[id]/narration` (page lifetime), and `/api/team/[id]/trace` (lifetime of an open trace surface: POV trace tab or dashboard play-by-play; the server pushes `update` events from a 2s store re-query of the trace JSONL). Sidebar, overview, and all settings pages fetch once on mount with manual refresh after writes; profile makes no API calls at all (localStorage only).

**Status vocabulary** — agents: `running | paused | errored | awaiting_approval` (green/gray/red/brand-blue dots, consistent across sidebar, dashboard, POV header, messages view); tasks: the eight A2AX states; platform: `healthy | degraded | maintenance`; trace tick threads: `live | finished | failed | awaiting_approval` (badges "live"/"done"/"failed"/"needs approval", `packages/frontend/src/lib/trace.ts:19` + `trace-view.tsx:24-29`).

**Token/cost numbers are synthetic everywhere** — the formula `(ticks_or_actions × 400 in, × 1200 out, $3/M + $15/M)` is duplicated in `src/app/(app)/page.tsx:91-93`, `src/app/(app)/f/[id]/team-view.tsx:93-95`, `packages/frontend/src/components/team/team-dashboard.tsx:84-86`, and `packages/frontend/src/components/team/agent-pov-view.tsx:348-350`. No real usage data is displayed — even though the backend records real token usage in the append-only spend ledger (`system/spend.jsonl`, via `recordSpend` at `packages/backend/src/server/api/tick.ts:429,552`), no UI surface reads it; the trace view shows per-step durations but no token counts. The overview's "Agent Spending" and "Income Generated" cards are hard-coded `$0.00` with "no integrations yet".

**Environment variables** — no UI file reads `process.env` (client or server); all configuration state comes from the settings API.

## Python backend (FastAPI port)

**There is no Python frontend.** The FastAPI port (`backend-py/`) re-implements only the backend (`packages/backend` + `packages/a2ax`); the UI described in this chapter — `packages/frontend` plus the Next.js App Router tree in `src/app/` — was explicitly **out of scope** and stays on Next.js/React, unchanged. The port's stated goal is to be a drop-in HTTP/WS peer "so the existing Next.js frontend can point at either one unchanged" ([`backend-py/ARCHITECTURE.md`](../backend-py/ARCHITECTURE.md)). What follows is therefore short: it documents *why* the frontend needs no edits, and the one-file cutover that swings it onto the Python host.

### Why the UI is untouched: the wire contract holds

Every data path this chapter describes — the mount-time `fetch` loads, the 2s–30s polls, and the three SSE-over-fetch streams (`/api/chat`, `/api/team/[id]/narration`, `/api/team/[id]/trace`) — is wire-compatible with the Python backend because the port treats the JSON contract as non-negotiable. Two rules in particular keep the frontend's parsers happy:

- **camelCase field names are preserved.** The frontend reads `team.tickCount`, `entry.agentId`, `entry.actionType`, `entry.executedAt`, message `fromAgentId`/`channelId`/`channelType`, etc. directly off the JSON. Pydantic v2 models keep those exact TS JSON keys via `model_config = ConfigDict(populate_by_name=True)` (e.g. [`backend-py/simple_harmonic/a2ax/message.py`](../backend-py/simple_harmonic/a2ax/message.py), [`channel.py`](../backend-py/simple_harmonic/a2ax/channel.py), [`task.py`](../backend-py/simple_harmonic/a2ax/task.py)) and dump with `by_alias=True` (e.g. [`backend-py/simple_harmonic/a2ax/json_file_transport.py`](../backend-py/simple_harmonic/a2ax/json_file_transport.py)). Pydantic replaces Zod here purely as the validation/serialization layer — the bytes on the wire are identical, so none of the field accesses in `use-team.ts`, `agent-messages-view.tsx`, or `trace.ts` change.
- **Datetimes serialize to ISO-8601 with a trailing `Z`.** The relative-time and "centered timestamp when >5 minutes elapse" logic, the trace view's `emittedAt`/`executedAt` sorting, and the narration `executedAt` field all parse ISO strings exactly as they did against `JSON.stringify(Date)`. The Python store reproduces that byte-for-byte via `_to_iso_z` / `json_default` in [`backend-py/simple_harmonic/store/serialize.py`](../backend-py/simple_harmonic/store/serialize.py) (UTC, millisecond precision, trailing `Z`).

The SSE surfaces are served by FastAPI `StreamingResponse` with `media_type="text/event-stream"` at the same paths the frontend opens: the planner stream at `POST /api/chat` ([`backend-py/simple_harmonic/routes/core.py`](../backend-py/simple_harmonic/routes/core.py)), and narration + trace at `GET /api/team/{id}/narration` / `GET /api/team/{id}/trace` ([`backend-py/simple_harmonic/routes/team.py`](../backend-py/simple_harmonic/routes/team.py)). The frames keep the same `data: …\n\n` framing the client splits on, the chat frames are deliberately byte-matched to `chat.ts`, and the live-poll cadences default to the TS values (3s narration / 2s trace — `NARRATION_POLL_S` / `TRACE_POLL_S` in `team.py`), so the client-side dedupe/append loops behave identically.

### Load-bearing fidelity behaviors the UI depends on

Two register items from [`backend-py/ARCHITECTURE.md`](../backend-py/ARCHITECTURE.md#fidelity-risk-register-load-bearing-behaviors-discovered-during-mapping) are exactly the ones this chapter's UI quirks lean on, and the port preserves them so the frontend keeps working — bugs and all:

- **`directChannelId` sorts the pair** (`direct:{min}:{max}`) and `broadcastChannelId` is `team:{teamId}` (register #7). `AgentMessagesView`'s client-side placeholder threads (`direct:<sortedIdA>:<sortedIdB>`) only merge cleanly with server threads because the Python channel-id derivation matches the TS scheme; the documented broadcast double-listing reproduces identically, since the Python backend returns the same `team:<teamId>` channel id the placeholder doesn't predict.
- **Selective date revival** (register #2) keeps ISO-looking strings *inside* `payload`/`metadata` as strings. Narration's `extractDetail(payload)` and the trace view's pretty-printed tool args/results render those nested values verbatim — the port's `revive_dates` only revives declared top-level `DATE_KEYS`, so the UI sees the same un-coerced payload strings it does today.

### The cutover: one env-gated file

The cutover is the single change in [`next.config.ts`](../next.config.ts) (the only frontend-side file the port touches). When `PY_BACKEND_URL` is set (e.g. `http://localhost:3001`), a `rewrites()` block with a `beforeFiles` rule forwards `/api/:path*` to the Python host, taking precedence over the filesystem API routes in `src/app/api/`. Unset (the default), behavior is unchanged and the in-repo Next route handlers serve. Because both runtimes share the same `.simple-harmonic/data/` store, the two can run side by side and the env var flipped on/off to compare them (see [`backend-py/MIGRATION.md`](../backend-py/MIGRATION.md) → "Run it"). This is slice 9 of the migration plan, and the only divergences relevant to the UI are latency-only, not behavioral: per-team agents run sequentially rather than via `Promise.allSettled`, and SSE teardown uses async-generator `GeneratorExit` rather than the TS `ReadableStream.cancel()` callback — neither changes a byte the frontend reads (see the "Deferred / known divergences" list in [`backend-py/MIGRATION.md`](../backend-py/MIGRATION.md)).
